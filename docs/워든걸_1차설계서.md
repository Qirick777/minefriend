# 워든걸 (WardenGirl) — 1차 설계서

**환경:** Minecraft 1.20.1 / Forge / Java 17
**1차 범위:** 애니메이션 뼈대 전용. 기능·AI·전투 판정 일절 제외
**문서 성격:** 구현 지시서. 이 문서에 없는 것은 만들지 않는다

---

## Part 0. 구현자 준수사항

이 문서를 읽는 구현자(Claude Code)는 다음을 반드시 지킨다.

1. **애니메이션 수치를 임의로 바꾸지 않는다.** Part 4의 모든 각도·틱·이징은 확정값으로 취급한다. "더 자연스러워 보이도록" 조정하는 것을 금지한다. 조정 권한은 사람에게만 있다.
2. **문서에 없는 동작을 추가하지 않는다.** 애니메이션, 파티클, 사운드, AI, 판정 전부.
3. **태스크를 건너뛰지 않는다.** Part 5의 T0부터 순서대로. 각 태스크 종료 시 반드시 멈추고 사람의 확인을 받는다.
4. **한 태스크를 완료했다고 다음으로 자동 진행하지 않는다.** 사람이 게임에서 눈으로 보고 판정해야 하는 구조다.
5. **불확실한 사항은 임의 결정하지 않고 질문한다.** 특히 라이브러리 버전, API 시그니처.
6. **완료 보고 시 "구현했다"가 아니라 "무엇이 어떻게 검증되었다"를 쓴다.** Part 6 참조.

## Part 1. 프로젝트 정의

### 1.1 무엇을 만드는가

플레이어 슬림 모델(알렉스) 외형의 **동료형 몹**. 이름 "워든걸".

| 축 | 내용 |
|---|---|
| **외형** | 슬림 휴머노이드 + 워든 머리 장식 1점. 갑옷 미착용 |
| **성격** | 귀여움 / 호감. 플레이어에게 애착을 보이는 동료 |
| **능력** | 워든 계승 — 소닉붐, 돌진 밀어내기 |

### 1.2 핵심 컨셉

**"플레이어처럼 보이는데 명백히 플레이어가 아닌 리듬으로 움직이는 존재."**

실루엣이 익숙하기 때문에 움직임의 이질감이 더 선명하게 읽힌다. 사람은 통통 튀지 않고, 고개를 12도 기울이지 않고, 안짱다리로 서지 않는다. 새 모델을 만들지 않고도 정체성을 확보하는 방법이 여기에 있다.

방향은 **언캐니가 아니라 과장**이다. 낯설게 만드는 것이 아니라, 귀엽게 과장해서 사람이 아니게 만든다.

### 1.3 갭 모에

귀여운 몹이 워든의 60틱 축력 동작을 온 힘을 다해 수행하는 대비가 캐릭터 서사의 중심이다.

**강해 보이는 게 아니라, 작은 것이 최선을 다하는 것으로 읽혀야 한다.** 축력 중 팔이 떨리고, 발포 후 반동으로 주춤 밀려나고, 끝나면 플레이어를 돌아본다.

## Part 2. 왜 1차를 애니메이션만으로 분리하는가

### 2.1 AI는 애니메이션의 품질을 볼 수 없다

기능 코드는 검증 가능하다. 변수가 바뀌었는지, 데미지가 들어갔는지는 값으로 확인된다. 그러나 **"이 동작이 자연스러운가"는 값으로 표현되지 않는다.**

구현자는 키프레임을 논리적으로 배치할 수 있지만 결과가 화면에서 어떻게 보이는지 알 수 없다. 무릎이 반대로 꺾여도, 착지가 반박자 늦어도 코드상으로는 아무 문제가 없다.

**따라서 애니메이션 단계의 판정자는 반드시 사람이다.** 구현자는 명세를 코드로 옮기는 역할에 머문다. 이 역할 분담이 성립하려면 애니메이션이 독립 단계로 떨어져 있어야 한다.

### 2.2 기능이 섞이면 판정이 오염된다

소닉붐이 어색하다고 느꼈을 때, 기능이 함께 있으면 원인이 다음 중 무엇인지 알 수 없다.

- 축력 포즈 자체가 빈약함
- 발포 판정 틱과 애니메이션 최고점이 어긋남
- AI가 사거리 판단을 늦게 해서 시작이 밀림
- 이동 정지 처리 누락으로 발이 미끄러짐

**애니메이션만 있는 상태에서 눈으로 먼저 확정해두면, 이후 문제는 전부 기능 쪽으로 좁혀진다.**

### 2.3 애니메이션은 다른 모든 것의 토대다

호흡·바운스·시선이라는 상시 레이어 위에 나머지 전부가 얹힌다. 기본 리듬이 흔들린 상태로 공격 모션을 만들면, 나중에 기본 리듬을 고칠 때 **위에 쌓은 것 전부를 다시 만져야 한다.**

### 2.4 튜닝은 사람이 직접 돌리는 게 압도적으로 빠르다

"바운스 0.4가 부족하다"를 구현자에게 말하고 코드를 받아 다시 넣는 왕복은 수 분이 걸린다. 상수 하나 바뀌는 일에 그 비용은 부당하다.

그래서 **1차의 산출물은 완성된 애니메이션이 아니라, 사람이 직접 돌릴 수 있는 노브가 노출된 애니메이션 시스템**이다. GeckoLib json + F3+T 리로드로 3초 왕복을 만든다.

### 2.5 페이즈 구성

| 페이즈 | 내용 | 판정자 |
|---|---|---|
| **1차** | 애니메이션 뼈대. 본 구조, 레이어, 전 동작 모션 | **사람의 눈** |
| 2차 | AI Goal, 공격 판정, 데미지, 파티클, 사운드, 실제 이동 | 자동 검증기 |
| 3차 | 길들이기, 소유자, 소환/해제, 밸런싱 | 자동 검증기 |

**1차에서 확정된 애니메이션 수치는 2차에서 다시 건드리지 않는다.**

## Part 3. 기술 스택 및 프로젝트 규격

### 3.1 기술 선택과 근거

| 항목 | 결정 | 근거 |
|---|---|---|
| 애니메이션 시스템 | **GeckoLib 4** | 아래 3.2 참조 |
| 저작 방식 | **구현자가 json 직접 작성** | 사람이 Blockbench 애니메이션 작업을 하지 않는다 |
| 모델 | GeckoLib geo.json (슬림 휴머노이드) | 바닐라 `HumanoidModel` 미사용 |
| 갑옷 | 미착용 | 진폭 제약 해제 |
| 시점 | 3인칭 전용 | 몹이므로 문제 없음 |

### 3.2 GeckoLib을 쓰는 이유

바닐라 `AnimationDefinition`이 아닌 이유는 다섯 가지다.

1. **`lerp_mode: catmullrom`** — 키프레임 사이를 스플라인 곡선으로 잇는다. 뻣뻣함의 대부분이 여기서 해결된다. 바닐라는 프리셋 보간만 가능하다.
2. **키프레임 단위 이징** — `easeOutBack`으로 오버슈트를, `easeInSine`으로 급발진을 한 줄로 만든다.
3. **키프레임 값에 Molang 삽입** — 축력 포즈에 떨림을 키프레임 자체에 얹을 수 있다. 레이어 분리조차 불필요.
4. **컨트롤러 분리** — 레이어가 서로 덮어쓰지 않는다. 바닐라 `KeyframeAnimations.animate()`는 회전값을 대입하므로 상시 레이어가 지워지는 문제가 있다. GeckoLib에서는 이 문제가 발생하지 않는다.
5. **F3+T 3초 리로드** — json은 리소스팩이다. 재컴파일이 없다. **이것이 실질적으로 품질을 결정한다.** 첫 시도에 타이밍이 어긋나는 것은 확실하고, 왕복이 3초면 20번 고쳐도 부담이 없다.

**`AnimParams.java`는 단일 파일로 유지한다.** 파라미터가 흩어지면 튜닝이 불가능해진다.

**`Bones.java` / `AxisConvention.java`는 `anim/`에 둔다.** 커맨드(서버 측)와 모델(클라이언트 측)이 둘 다 참조하므로 어느 한쪽 패키지에 둘 수 없다. 클라이언트 전용 클래스를 커맨드에서 참조하면 전용 서버에서 터진다.

**`AxisConvention.java`는 부호 반전 테이블이 아니다.** 역할은 두 가지다.
1. **규약 문서화** — 4.0.1 규약과 본별 유도표를 코드 측에 단일 출처로 보유
2. **각도 → 라디안 변환의 단일 지점** — GeckoLib `GeoBone`에 값을 넣기 직전의 유일한 변환 경로

부호는 어디에서도 뒤집지 않는다. 이유는 4.0.1 하단 참조.

### 3.6 파라미터 노출 방식

**Forge Config (TOML) + 커맨드 직접 변경.** 둘 다 구현한다.

- TOML: `config/wardengirl-client.toml`. 파일 저장 후 커맨드로 리로드
- 커맨드: `/wardengirl param set <key> <value>` — 즉시 반영, 재접속 시 초기화

근거: 파라미터 30여 개를 각각 5회만 조정해도 150회 왕복이다. Java 상수로 가면 여기서 몇 시간이 소요된다. 초기 투자 30분으로 회수된다.

**Molang 수식 내부의 상수(호흡·바운스 등)는 json에 있으므로 F3+T로 즉시 반영된다.** TOML/커맨드는 Java 측 값(스프링 상수, 시선 감쇠, idle 간격 등)에 쓴다.

### 3.7 모델 규격

바닐라 알렉스 스킨 구조를 GeckoLib geo.json으로 재현한다.

| 파츠 | 크기(px) | 피벗 |
|---|---|---|
| **hip** | **큐브 없음** | **(0, 12, 0)** |
| head | 8×8×8 | (0, 24, 0) |
| body | 8×12×4 | **(0, 12, 0)** |
| arm_right | **3**×12×4 | (-5, 22, 0) |
| arm_left | **3**×12×4 | (5, 22, 0) |
| leg_right | 4×12×4 | **(-2.0, 12, 0)** |
| leg_left | 4×12×4 | **(2.0, 12, 0)** |

**팔 너비 3px (슬림).** 4px이면 클래식이 되어 컨셉이 무너진다.

**다리 피벗은 ±2.0이다.** 큐브도 피벗 중심으로 두어(`x = -4~0`, `0~4`) 두 다리가 정확히 맞닿는다. **피벗만 옮기면 겹침은 그대로 남는다** — 겹침을 만드는 것은 큐브 위치이기 때문이다. 근거는 Part 11.

**`hip`은 큐브가 없다.** 피벗만 존재하는 보이지 않는 본이며, 다리(`leg_right` / `leg_left`)와 `body`를 자식으로 갖는다. **`body` 피벗은 목(0, 24, 0)이 아니라 골반(0, 12, 0)이다** — 큐브 자체는 여전히 y 12~24를 차지한다. 근거는 Part 4.0 및 Part 11.

**headgear (워든 머리 장식) — 1차 임시 규격:**
- `head`의 자식. 피벗 (0, 32, 0)
- 형태: 머리 위에 얹히는 좌우 한 쌍의 돌기. 각 2×5×2 정도, 좌우로 살짝 벌어짐
- **텍스처와 정확한 형태는 1차에서 확정하지 않는다.** 관성 물리 검증용 임시 형태로 충분하다. 사람이 보고 좌표를 지시한다

텍스처: `warden_girl.png` 64×64 슬림 레이아웃. **1차에서는 단색 또는 임시 스킨.** 사람이 나중에 교체한다. 파일이 없으면 T1에서 막히므로 구현자가 임시 파일을 생성한다.

```

체력        : 20 (임시, 2차에서 조정)

히트박스    : 0.6 × 1.8 (플레이어와 동일)

```

## Part 4. 애니메이션 명세

> **이 Part는 v2 개정판으로 전면 교체되었다.** 근거: T1 축 검증 캡처 전량, 3차 규약 확정, `hip` 본 신설, 그리고 구현자가 제출한 감사 후보 목록. 변경 요약은 4.11, 개정 이력은 Part 11.


### 4.0 규약 (확정. 재검증 완료)

#### 4.0.1 회전 부호

기준점은 **피벗 바로 위의 점**. y축만 **피벗 바로 앞의 점**.

- `+xRot` : 기준점이 몹의 **뒤(-Z)** 로
- `+yRot` : 기준점(앞)이 몹의 **왼쪽(+X)** 으로 = 위에서 볼 때 반시계
- `+zRot` : 기준점이 몹의 **왼쪽(+X)** 으로

#### 4.0.2 본별 물리적 의미 (위에서 유도. 참조 전용)

| 본 | + | − |
|---|---|---|
| hip / body **xRot** | 뒤로 젖힘 | **앞으로 숙임** |
| hip / body **yRot** | 왼쪽 비틀기 | 오른쪽 비틀기 |
| hip / body **zRot** | 왼쪽 기울임 | 오른쪽 기울임 |
| head **xRot** | **위를 봄** | 아래를 봄 |
| head **yRot** | 왼쪽을 봄 | 오른쪽을 봄 |
| head **zRot** | 왼쪽 갸웃 | 오른쪽 갸웃 |
| arm / leg **xRot** | **앞으로** | 뒤로 |
| arm_right / leg_right **zRot** | 바깥으로 벌림 | 안쪽으로 붙임 |
| arm_left / leg_left **zRot** | 안쪽으로 붙임 | 바깥으로 벌림 |

> **좌우 zRot 부호가 반대다.** 대칭 동작은 반드시 좌우를 따로 적는다. `±` 표기 금지.

#### 4.0.3 각도 단위

문서의 모든 각도는 **도(degree)**. 라디안 변환은 `AxisConvention`의 단일 지점에서만. 부호는 어디서도 뒤집지 않는다.

#### 4.0.4 본 계층 (9개)

```
root                      위치 전용 (y, z 이동). 회전 미사용
└ hip                     전신 기울임 · 체중이동. 피벗 (0,12,0), 큐브 없음
  ├ body                  상체. 피벗 (0,12,0), 큐브 y12~24
  │ ├ head                피벗 (0,24,0)
  │ │ └ headgear          물리 전용. 키프레임 금지
  │ ├ arm_right           피벗 (-5,22,0)
  │ └ arm_left            피벗 (5,22,0)
  ├ leg_right             피벗 (-1.9,12,0)
  └ leg_left              피벗 (1.9,12,0)
```

#### 4.0.5 hip vs body 사용 기준 (신설)

| 의도 | 본 |
|---|---|
| 상체만 숙이거나 젖힘 (호흡, 기지개, 축력) | **body** |
| 다리 포함 전신 기울기 (돌진, 착지 충격) | **hip** |
| 좌우 체중 이동 | **hip** |
| 상체 좌우 흔들림 (미세 sway) | body |
| 전신 상하 이동 | **root.y** |
| 흉곽만 상승 | body.y |

**중요:** hip을 회전시키면 다리가 따라 돈다. 다리를 세워두려면 leg에 역회전을 넣어야 한다 (4.10.2 참조).

몸통에서 시작해 말단으로 전파. 각 본의 키프레임 시각을 지연만큼 뒤로 민다.

### 원칙 2 — 반대회전

`leg 양쪽 yRot = -body.yRot × 0.4`

머리는 시선 수평 유지 보정 (전정안반사):
`head.xRot 보정 = -body.xRot × 0.5`

### 원칙 3 — 무게중심 보상

- 팔을 앞으로 뻗음(+x) → `body.xRot`을 **+**(뒤로) 방향으로 (뻗은 각도 × 0.12)
- 한쪽 다리에 체중 → **`hip.zRot`** 을 그쪽으로, `head.zRot`을 반대로
- 앞으로 돌진 → `leg.xRot`을 **−**(뒤로)로 뻗어 지지

### 원칙 4 — 예비동작

모든 동작은 반대 방향으로 먼저 움직인다. 진폭 25%, 6틱 전.

### 원칙 5 — 오버슈트와 정착

배율 1.15~1.25배, 정착 4~6틱. 도달 `easeOutBack`, 정착 `easeOutSine`.

### 원칙 6 — 완전 정지 금지

C1은 꺼지지 않는다. 예외는 소닉붐 0~3틱뿐.

### 4.3 C1 상시 레이어 (Molang)

#### 4.3.1 호흡 (주기 44tick)

들숨에 흉곽이 오르고 상체가 살짝 젖혀지며, 머리는 수평을 유지하려 반대로 보정한다.

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| body | xRot | `0.5 * sin(t*8.2)` | 들숨에 뒤로 젖힘 |
| body | y | `0.12 * sin(t*8.2)` | 흉곽 상승 (px) |
| head | xRot | `-0.25 * sin(t*8.2 - 16)` | 수평 유지 보정 |
| arm_right | zRot | `0.35 * (1 + sin(t*8.2 - 12))` | 바깥으로만. 범위 0 ~ +0.7 |
| arm_left | zRot | `-0.35 * (1 + sin(t*8.2 - 12))` | 바깥으로만. 범위 0 ~ -0.7 |

**다리는 호흡에서 뺀다.** (구판 `leg xRot -0.2` 삭제)

**`8.2 = 360/44`.** 구현에서는 주기(44틱)를 파라미터로 두고 `360/주기`로 환산한다 — 사람이 판단하는 단위는 "틱당 몇 도"가 아니라 "한 번에 몇 틱"이다.

> **팔 zRot에 바깥 방향 바이어스를 건다.** 팔 안쪽면과 몸통 바깥면은 `x = ±4`로 **간격이 0**이라, 안쪽으로 가는 각도는 크기와 무관하게 즉시 관통한다. `(1 + sin)` 형태는 값을 `0 ~ 2×진폭`으로 만들어 **바깥으로만** 진동시킨다. 중립에서 시작해 벌어졌다 돌아오므로 "들숨에 어깨가 벌어진다"는 원래 의도도 유지된다. 계산 근거는 Part 11.

**[의도 크기]** 자세히 보면 알 정도. 시선을 끌면 과함.

> 구판 대비 변경: 주기 30 → **44틱**(분당 40회 → 27회), `body.xRot` 0.7 → 0.5, `head.xRot` 0.35 → 0.25, `arm zRot` 0.5 → 0.35(+바이어스), 다리 삭제. 30틱은 사람 안정 시 호흡의 3배 가까이 빨라 "까딱까딱"으로 읽혔다.

#### 4.3.2 바운스 (주기 25tick)

| 본 | 축 | 수식 |
|---|---|---|
| root | y | `0.4 * sin(t*7.2)` |

**순수 sin을 쓴다. `abs()`를 쓰지 않는다.**

절댓값은 바닥에서 튕기는 리듬을 만든다. 그 리듬은 "가만히 서 있는 존재"가 아니라 **"제자리 뛰기 하는 존재"**로 읽힌다 — 상시 레이어에는 부적합하다. `abs`를 빼면 실질 주기가 12.5틱에서 **25틱**으로 늘어나 느긋한 상하 호흡감이 된다.

접지 충격이 사라지므로 **다리 벌림(`leg zRot`)도 함께 폐기한다.** 흡수할 충격 자체가 없다.

**정지 상태 기본값은 `0.0`이다. 사용자 판정.** 서 있는 동료가 위아래로 통통거릴 이유가 없다.

**수식과 파라미터는 삭제하지 않고 남긴다.** T5 걷기에서 *이동 중* 바운스가 필요할 수 있다. "제거"가 아니라 "정지 상태에서만 0"이다.

**[의도 크기]** 정지 상태 `0.0` 확정.

#### 4.3.3 미세 흔들림 (주기 53tick)

호흡·바운스와 주기가 서로소에 가까워 위상이 계속 어긋난다. 반복 감지가 되지 않는 이유다.

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| body | zRot | `1.2 * sin(t*6.8)` | 상체 좌우 |
| head | zRot | `-0.7 * sin(t*6.8 - 14)` | 반대 보정 |
| hip | yRot | `0.5 * sin(t*6.8 - 20)` | 전신 미세 비틀기 |

`6.8 = 360/53`. 구판 대비 진폭 상향(0.8→1.2, 0.5→0.7, 0.3→0.5). 호흡 진폭을 줄인 만큼 좌우 축의 비중을 키워 단일축 진자 인상을 깬다.

> 구판 오류 수정: `leg 양쪽 yRot -0.3`은 좌우 같은 부호여서 "발끝 안쪽"이 성립하지 않았다. 구 규약 기준으로도 모순이었다. hip.yRot으로 대체. (감사 후보 B-5)

#### 4.3.4 기본 자세 오프셋 (정적, 상시 가산)

비인간 실루엣의 절반이 여기서 나온다.

| 본 | 축 | 값 | 의도 |
|---|---|---|---|
| arm_right | **xRot** | **+4** | 힘 빼고 살짝 앞으로 |
| arm_left | **xRot** | **+4** | 힘 빼고 살짝 앞으로 |
| leg_right | yRot | **+2** | 안짱 (발끝이 +X로) |
| leg_left | yRot | **-2** | 안짱 (발끝이 -X로) |
| head | xRot | **-3** | 목 앞으로 |
| body | xRot | **-1.5** | 어깨 앞으로 |

> **팔은 zRot이 아니라 xRot이다.** 의도는 "좌우로 모은다"가 아니라 **"힘을 빼고 자연스럽게 늘어뜨린다"**이다. 사람이 편하게 설 때 팔은 좌우로 모이지 않고 살짝 앞으로 온다. `body.xRot -1.5`(어깨 앞으로)와도 이어진다.
>
> **기하학적으로도 zRot은 불가능하다.** 팔 안쪽면과 몸통 바깥면이 둘 다 `x = ±4`로 **맞닿아 있다**(간격 0). 안쪽으로 도는 zRot은 각도와 무관하게 즉시 몸통을 파고든다. `-4°`면 침투 **0.70px**이다. xRot은 앞뒤 회전이라 z평면에서 충돌할 대상이 없다. 계산 근거는 Part 11.

**[의도 크기]** 정지 상태에서 "사람 자세가 아니다"가 읽힐 정도. 과하면 구부정한 노인이 된다.

> **관통 2건 처리 완료.** 4.3.1 호흡 팔 zRot은 **바깥 방향 바이어스**로, 양다리 0.20px 겹침은 **피벗·큐브 ±2.0**으로 해결됐다. 남은 것은 안짱 오프셋의 모서리 스윕 **0.099px** 하나이며, 육안 식별 불가 수준으로 판단해 **감수한다.** 근거는 Part 11.

#### 4.3.5 체중 이동 (주기 79tick) — 신설

아주 느린 좌우 체중 이동이다. **세 번째 축이자 가장 느린 층.**

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| hip | zRot | `0.8 * sin(t*4.56)` | 좌우 체중 이동 (다리 포함) |
| head | zRot | `-0.4 * sin(t*4.56 - 24)` | 반대 보정 (4.3.3 항에 **가산**) |

`4.56 = 360/79`.

**79는 44/53과 공배수가 없다.** 세 주기가 절대 같은 조합으로 되돌아오지 않는다. **이것이 "규칙적 반복"을 깨는 핵심이며, 진폭이 아니라 위상 설계의 문제다.**

`head.zRot`은 4.3.3의 흔들림 보정과 이 항의 **합**이다. 덮어쓰지 않는다.

**[의도 크기]** 의식적으로 보이면 안 된다. "가만히 있는데 미묘하게 계속 다르다" 수준.

### 4.5 headgear 물리 (키프레임 금지)

#### 4.5.1 감쇠 스프링

각 축 독립. **단위는 도(degree).**

```
targetDeg   = head의 현재 각도 (도)
velocityDeg += (targetDeg - angleDeg) * STIFFNESS - velocityDeg * DAMPING
angleDeg    += velocityDeg
```

| 상수 | 값 |
|---|---|
| `STIFFNESS` | 0.25 |
| `DAMPING` | 0.35 |
| `AMPLITUDE` | 1.3 |
| `MAX_ANGLE` | 35 (도) |

**최종 적용:** `headgear.rotationDeg = clamp((angleDeg - targetDeg) * AMPLITUDE, ±MAX_ANGLE)`

> **차이값을 쓴다.** headgear는 head의 자식이라 head 회전은 이미 상속된다. 얹는 것은 지연 오차분뿐이다. 놓치면 장식이 두 배로 돈다.

`partialTick` 보간 필수.

#### 4.5.2 상태별 상수

| 상황 | STIFFNESS |
|---|---|
| 기본 | 0.25 |
| 소닉붐 축력 | 0.40 |
| 소닉붐 발포 | 0.15 |
| 돌진 중 | 0.18 |

**[의도 크기]** **T2/T3 튜닝 2순위.** 값에 매우 민감하다. 발산하면 DAMPING을 올린다.

## Part 5. 태스크 분할

각 태스크는 **독립적으로 눈으로 확인 가능한 단위**다.
**구현자는 한 태스크를 완료하면 반드시 멈추고 사람의 확인을 받는다. 자동 진행 금지.**

각 태스크는 두 종류의 완료 조건을 갖는다.

- **[기계 검증]** — 구현자가 확인 가능. 값·상태·로그로 판정
- **[사람 확인]** — 사람이 게임에서 눈으로 판정. **구현자는 이 항목을 스스로 판정하지 않는다**

## Part 6. 검증 체계

### 6.1 1차 검증의 성격

1차의 최종 판정자는 **사람의 눈**이다. 애니메이션 품질은 자동 검증되지 않는다.

그러나 커맨드는 필요하다. 목적이 다르다.

- **1차 커맨드의 목적:** 보고 싶은 순간을 즉시 만드는 것
- **2차 커맨드의 목적:** 기능이 작동했는지 값으로 판정하는 것

**1차 커맨드도 2차와 같은 원칙으로 만든다.** 2차에서 재작업하지 않기 위해서다.

### 6.2 가짜 검증 금지 — 두 원칙

#### 원칙 1: 상황을 실제로 조성한다

커맨드는 "지금 소닉붐 애니메이션 38틱 시점"을 **즉시 만들어야** 한다.

**금지:** 조건이 갖춰지길 기다리기. 상황을 흉내내는 로그만 출력하기. "재생을 요청했습니다"로 끝내기.

보고 싶은 시점에 즉각 그 시점을 만드는 것이 커맨드의 존재 이유다.

#### 원칙 2: 호출 성공을 성공으로 취급하지 않는다

커맨드가 오류 없이 실행됐다는 것은 **아무것도 증명하지 않는다.**

판정은 **결과의 변화, 변수의 변동**으로 한다.

- 애니메이션 상태가 실제로 시작됐는가 (`isActive`, 경과 틱 > 0)
- 경과 틱이 증가하고 있는가
- 대상 본의 회전값이 실제로 변했는가 (호출 전/후 비교)
- 파라미터를 바꿨으면 다음 프레임의 본 값이 달라졌는가

**커맨드는 이 값들을 출력해야 한다.** "성공"이라는 문자열만 출력하는 커맨드는 이 프로젝트에서 실패로 취급한다.

### 6.3 1차 필요 커맨드

| 커맨드 | 동작 | 출력 (필수) |
|---|---|---|
| `/wardengirl summon [pos]` | 즉시 소환 | 엔티티 UUID, 위치 |
| `/wardengirl axistest <bone>` | 본을 각 축 +10° 회전 후 정지 | 적용된 각도 3축 |
| `/wardengirl anim play <name>` | **조건 무시하고 즉시 재생** | 재생 전/후 컨트롤러 상태, 경과 틱 |
| `/wardengirl anim stop` | C3 초기화 | 정지된 컨트롤러명, 잔여 본 오프셋 |
| `/wardengirl anim freeze <tick>` | **지정 틱에서 고정** | 고정 틱, 그 시점 전 본의 회전값 8×3 |
| `/wardengirl anim step <n>` | freeze 상태에서 n틱 진행 | 진행 후 본 회전값 |
| `/wardengirl state` | 현재 상태 조회 | C1/C2/C3 각 재생명·경과틱, 본 9개 회전값, headgear 스프링 각도/속도, 시선 목표/현재 |
| `/wardengirl param list` | 파라미터 전체 | key = 현재값 (기본값 표시) |
| `/wardengirl param set <k> <v>` | 즉시 변경 | 변경 전값 → 후값, **다음 프레임 영향 본 값** |
| `/wardengirl param reload` | TOML 재로드 | 변경된 key 목록 |
| `/wardengirl ai <on\|off>` | 임시 AI 토글 (걷기 확인용) | 활성 Goal 목록 |

**`anim freeze` + `state`가 1차의 핵심 도구다.** 축력 최고점이나 발포 순간의 포즈를 정지 상태로 관찰할 수 있어야, 흐르는 동작에서 놓치는 문제를 잡을 수 있다.

### 6.4 사람 ↔ 구현자 피드백 프로토콜

애니메이션 피드백의 정확도 순서:

1. **최선:** GIF 또는 짧은 영상
2. **좋음:** `anim freeze` 후 특정 틱의 스크린샷
3. **가능:** "몇 틱에서 무엇이 어떻게" 형태의 구체적 서술
4. **비효율:** "부자연스럽다", "어색하다" 등 총평만

**구현자는 총평만 받았을 때 임의 수정하지 않고, 어느 틱의 어느 본이 문제인지 질문한다.**

### 6.5 완료 보고 형식

각 태스크 종료 시 구현자는 다음 형식으로 보고한다.

```
[T# 완료 보고]
구현: (무엇을 만들었는지)
기계 검증: (각 항목 — 무엇을 어떻게 확인했는지, 실제 값 포함)
사람 확인 요청: (게임에서 무엇을 어떤 커맨드로 봐야 하는지)
미결/질문: (있으면)
```

**"구현 완료" 단독 보고를 금지한다.**

## Part 7. 튜닝 프로토콜

### 7.1 이 단계의 성격

**1차는 사람이 눈으로 보고 값을 정하는 단계다.** 구현자는 명세를 코드로 옮기고 노브를 노출한다. 값의 최종 결정권은 사람에게 있다.

Part 4의 수치는 **논리적으로 설계된 시작점이며 확정값이 아니다.** 실제로 보면 여러 개가 어긋나 있을 가능성이 높다.

### 7.2 튜닝 우선순위

위에서부터 확정한다.

| 순위 | 대상 | 초기값 | 왜 먼저인가 |
|---|---|---|---|
| 1 | `BOUNCE_AMPLITUDE` | 0.4px | 슬림 모델에서 과할 가능성 높음. 전체 인상 결정 |
| 2 | headgear `STIFFNESS` / `DAMPING` | 0.25 / 0.35 | 관성 품질의 핵심. 값에 매우 민감 |
| 3 | `BREATH_AMPLITUDE` | 0.7° | 모든 동작의 기저 |
| 4 | 고개 갸웃 `head.zRot` | 12° | 과하면 목이 꺾인 것처럼 보임 |
| 5 | 소닉붐 축력 팔 각도 | -112° | 슬림 모델 빈약함 방지 |
| 6 | 걷기 팔 스윙 | ±10° | 플레이어 실루엣 탈피 |

### 7.3 왕복 비용

| 대상 | 반영 방법 | 소요 |
|---|---|---|
| json 내 수식·키프레임 | F3+T | ~3초 |
| Java 파라미터 | `/wardengirl param set` | 즉시 |
| TOML | 저장 후 `param reload` | ~5초 |
| 구조 변경 | 재컴파일 | ~2분 |

**구조 변경이 필요한 수정을 최소화하도록 설계했다.** 튜닝 대상은 전부 상위 3개 경로로 처리되어야 한다.

1. **한쪽으로만 간다.** `0.7*sin`은 -0.7~+0.7을 오가야 하는데 정적 오프셋 `body.xRot -1.5`가 중심이라 실제 구간이 **-2.2 ~ -0.8**이다. 항상 앞으로 숙인 상태에서만 진동하고 뒤로 젖히는 국면이 없다.
2. **축이 하나뿐.** xRot이 살아 있는 본이 `body`와 `head`뿐이고 둘 다 앞뒤 회전이다. 단일축 진자.
3. **주기가 짧다.** 30틱 = 1.5초 = 분당 40회. 사람 안정 시 호흡의 3배 가까이 빠르다.

**변경.**

| | 구판 | 신판 |
|---|---|---|
| 호흡 주기 | 30틱 | **44틱** (분당 27회) |
| `body.xRot` | 0.7 | 0.5 |
| `body.y` | 0.15 | 0.12 |
| `head.xRot` | 0.35 | 0.25 |
| `arm zRot` | 0.5 | 0.35 (+바깥 바이어스) |
| `leg xRot` | 0.2 | **삭제** |
| `sway body.zRot` | 0.8 | **1.2** |
| `sway head.zRot` | 0.5 | **0.7** |
| `sway hip.yRot` | 0.3 | **0.5** |
| 체중 이동 (79틱) | 없음 | **신설** — `hip.zRot 0.8`, `head.zRot -0.4` |

**핵심은 진폭 축소가 아니라 축을 늘리고 주기를 벌린 것이다.** 앞뒤(44틱)·좌우(53틱)·체중이동(79틱) 세 축이 서로 다른 주기로 동시에 돌아가고, 세 수는 공배수가 없어 같은 조합이 반복되지 않는다.

**주기도 파라미터로 노출했다.** `breath_period` / `sway_period` / `weight_shift_period` / `bounce_period`. 진폭만으로는 "빠르다"는 인상을 고칠 수 없기 때문이다. 이에 맞춰 기존 `*_speed`(도/틱)를 `*_period`(틱)로 전부 바꿨다 — 사람이 판단하는 단위는 "틱당 몇 도"가 아니라 "한 번에 몇 틱"이다. json은 `360/주기`로 환산한다.

#### (3) 팔 zRot 관통 — 바깥 방향 바이어스

팔 안쪽면과 몸통 바깥면은 `x = ±4`로 **간격 0**이다. 안쪽으로 가는 각도는 크기와 무관하게 즉시 관통한다(0.5°에서 이미 0.087px). 따라서 **안쪽으로 가지 않게** 만든다.

```
arm_right zRot =  0.35 * (1 + sin(t*8.2 - 12))   → 범위 0 ~ +0.70  (전부 바깥)
arm_left  zRot = -0.35 * (1 + sin(t*8.2 - 12))   → 범위 0 ~ -0.70  (전부 바깥)
```

preset max(×4)에서도 범위는 `0 ~ ±2.80`으로 **안쪽 성분이 0**이다. 관통이 원천 차단된다.

#### (4) 다리 피벗 ±1.9 → ±2.0

**변경.** `leg_right` 피벗 `(-1.9,12,0)` → `(-2.0,12,0)`, 큐브 `x=[-3.9,0.1]` → `[-4.0,0.0]`. `leg_left` 대칭. 겹침 `0.20px` → **`0.00px`**.

**피벗만 옮기면 겹침은 그대로 남는다.** 겹침을 만드는 것은 큐브 위치이므로 큐브도 함께 옮겼다.

> **정정 — 구현자의 이전 보고 오류.** 이전 보고에서 "바닐라는 ±2를 써서 정확히 맞닿는다"고 했으나 **사실이 아니다.** 1.20.1 `HumanoidModel` 바이트코드 확인 결과 `left_leg`는 `addBox(-2,0,-2, 4,12,4)` + `PartPose.offset(1.9, 12, 0)`으로, **바닐라에도 동일한 0.2px 겹침이 있다.** 즉 초안의 ±1.9는 바닐라 정확값이었고, 이번 ±2.0 변경은 바닐라 복원이 아니라 **바닐라와 0.2px 다르게 만드는 의도적 개선**이다(다리 폭 총 7.8px → 8.0px). 겹침 제거라는 목적은 달성되므로 변경은 유지하되, 근거를 정정해 기록한다.

**남은 관통 1건은 감수한다.** 안짱 오프셋 `leg yRot ±2°`의 모서리 스윕 `0.099px`. 육안 식별 불가 수준. 보이면 그때 처리한다.
