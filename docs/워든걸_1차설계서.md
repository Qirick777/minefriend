# 워든걸 (WardenGirl) — 1차 설계서

**환경:** Minecraft 1.20.1 / Forge / Java 17
**1차 범위:** 애니메이션 뼈대 전용. 기능·AI·전투 판정 일절 제외
**문서 성격:** 구현 지시서. 이 문서에 없는 것은 만들지 않는다

---

## Part 0. 구현자 준수사항

이 문서를 읽는 구현자(Claude Code)는 다음을 반드시 지킨다.

1. **애니메이션 수치를 임의로 바꾸지 않는다.** Part 4의 모든 각도·틱·이징은 확정값으로 취급한다. "더 자연스러워 보이도록" 조정하는 것을 금지한다. 조정 권한은 사람에게만 있다.
2. **문서에 없는 동작을 추가하지 않는다.** 애니메이션, 파티클, 사운드, AI, 판정 전부.
3. **태스크를 건너뛰지 않는다.** Part 5의 T0부터 순서대로. 각 태스크 종료 시 반드시 멈추고 사람의 확인을 받는다.
4. **한 태스크를 완료했다고 다음으로 자동 진행하지 않는다.** 사람이 게임에서 눈으로 보고 판정해야 하는 구조다.
5. **불확실한 사항은 임의 결정하지 않고 질문한다.** 특히 라이브러리 버전, API 시그니처.
6. **완료 보고 시 "구현했다"가 아니라 "무엇이 어떻게 검증되었다"를 쓴다.** Part 6 참조.

## Part 1. 프로젝트 정의

### 1.1 무엇을 만드는가

플레이어 슬림 모델(알렉스) 외형의 **동료형 몹**. 이름 "워든걸".

| 축 | 내용 |
|---|---|
| **외형** | 슬림 휴머노이드 + 워든 머리 장식 1점. 갑옷 미착용 |
| **성격** | 귀여움 / 호감. 플레이어에게 애착을 보이는 동료 |
| **능력** | 워든 계승 — 소닉붐, 돌진 밀어내기 |

### 1.2 핵심 컨셉

**"플레이어처럼 보이는데 명백히 플레이어가 아닌 리듬으로 움직이는 존재."**

실루엣이 익숙하기 때문에 움직임의 이질감이 더 선명하게 읽힌다. 사람은 통통 튀지 않고, 고개를 12도 기울이지 않고, 안짱다리로 서지 않는다. 새 모델을 만들지 않고도 정체성을 확보하는 방법이 여기에 있다.

방향은 **언캐니가 아니라 과장**이다. 낯설게 만드는 것이 아니라, 귀엽게 과장해서 사람이 아니게 만든다.

### 1.3 갭 모에

귀여운 몹이 워든의 60틱 축력 동작을 온 힘을 다해 수행하는 대비가 캐릭터 서사의 중심이다.

**강해 보이는 게 아니라, 작은 것이 최선을 다하는 것으로 읽혀야 한다.** 축력 중 팔이 떨리고, 발포 후 반동으로 주춤 밀려나고, 끝나면 플레이어를 돌아본다.

## Part 2. 왜 1차를 애니메이션만으로 분리하는가

### 2.1 AI는 애니메이션의 품질을 볼 수 없다

기능 코드는 검증 가능하다. 변수가 바뀌었는지, 데미지가 들어갔는지는 값으로 확인된다. 그러나 **"이 동작이 자연스러운가"는 값으로 표현되지 않는다.**

구현자는 키프레임을 논리적으로 배치할 수 있지만 결과가 화면에서 어떻게 보이는지 알 수 없다. 무릎이 반대로 꺾여도, 착지가 반박자 늦어도 코드상으로는 아무 문제가 없다.

**따라서 애니메이션 단계의 판정자는 반드시 사람이다.** 구현자는 명세를 코드로 옮기는 역할에 머문다. 이 역할 분담이 성립하려면 애니메이션이 독립 단계로 떨어져 있어야 한다.

### 2.2 기능이 섞이면 판정이 오염된다

소닉붐이 어색하다고 느꼈을 때, 기능이 함께 있으면 원인이 다음 중 무엇인지 알 수 없다.

- 축력 포즈 자체가 빈약함
- 발포 판정 틱과 애니메이션 최고점이 어긋남
- AI가 사거리 판단을 늦게 해서 시작이 밀림
- 이동 정지 처리 누락으로 발이 미끄러짐

**애니메이션만 있는 상태에서 눈으로 먼저 확정해두면, 이후 문제는 전부 기능 쪽으로 좁혀진다.**

### 2.3 애니메이션은 다른 모든 것의 토대다

호흡·바운스·시선이라는 상시 레이어 위에 나머지 전부가 얹힌다. 기본 리듬이 흔들린 상태로 공격 모션을 만들면, 나중에 기본 리듬을 고칠 때 **위에 쌓은 것 전부를 다시 만져야 한다.**

### 2.4 튜닝은 사람이 직접 돌리는 게 압도적으로 빠르다

"바운스 0.4가 부족하다"를 구현자에게 말하고 코드를 받아 다시 넣는 왕복은 수 분이 걸린다. 상수 하나 바뀌는 일에 그 비용은 부당하다.

그래서 **1차의 산출물은 완성된 애니메이션이 아니라, 사람이 직접 돌릴 수 있는 노브가 노출된 애니메이션 시스템**이다. GeckoLib json + F3+T 리로드로 3초 왕복을 만든다.

### 2.5 페이즈 구성

| 페이즈 | 내용 | 판정자 |
|---|---|---|
| **1차** | 애니메이션 뼈대. 본 구조, 레이어, 전 동작 모션 | **사람의 눈** |
| 2차 | AI Goal, 공격 판정, 데미지, 파티클, 사운드, 실제 이동 | 자동 검증기 |
| 3차 | 길들이기, 소유자, 소환/해제, 밸런싱 | 자동 검증기 |

**1차에서 확정된 애니메이션 수치는 2차에서 다시 건드리지 않는다.**

## Part 3. 기술 스택 및 프로젝트 규격

### 3.1 기술 선택과 근거

| 항목 | 결정 | 근거 |
|---|---|---|
| 애니메이션 시스템 | **GeckoLib 4** | 아래 3.2 참조 |
| 저작 방식 | **구현자가 json 직접 작성** | 사람이 Blockbench 애니메이션 작업을 하지 않는다 |
| 모델 | GeckoLib geo.json (슬림 휴머노이드) | 바닐라 `HumanoidModel` 미사용 |
| 갑옷 | 미착용 | 진폭 제약 해제 |
| 시점 | 3인칭 전용 | 몹이므로 문제 없음 |

### 3.2 GeckoLib을 쓰는 이유

바닐라 `AnimationDefinition`이 아닌 이유는 다섯 가지다.

1. **`lerp_mode: catmullrom`** — 키프레임 사이를 스플라인 곡선으로 잇는다. 뻣뻣함의 대부분이 여기서 해결된다. 바닐라는 프리셋 보간만 가능하다.
2. **키프레임 단위 이징** — `easeOutBack`으로 오버슈트를, `easeInSine`으로 급발진을 한 줄로 만든다.
3. **키프레임 값에 Molang 삽입** — 축력 포즈에 떨림을 키프레임 자체에 얹을 수 있다. 레이어 분리조차 불필요.
4. **컨트롤러 분리** — 레이어가 서로 덮어쓰지 않는다. 바닐라 `KeyframeAnimations.animate()`는 회전값을 대입하므로 상시 레이어가 지워지는 문제가 있다. GeckoLib에서는 이 문제가 발생하지 않는다.
5. **F3+T 3초 리로드** — json은 리소스팩이다. 재컴파일이 없다. **이것이 실질적으로 품질을 결정한다.** 첫 시도에 타이밍이 어긋나는 것은 확실하고, 왕복이 3초면 20번 고쳐도 부담이 없다.

**`AnimParams.java`는 단일 파일로 유지한다.** 파라미터가 흩어지면 튜닝이 불가능해진다.

**`Bones.java` / `AxisConvention.java`는 `anim/`에 둔다.** 커맨드(서버 측)와 모델(클라이언트 측)이 둘 다 참조하므로 어느 한쪽 패키지에 둘 수 없다. 클라이언트 전용 클래스를 커맨드에서 참조하면 전용 서버에서 터진다.

**`AxisConvention.java`는 부호 반전 테이블이 아니다.** 역할은 두 가지다.
1. **규약 문서화** — 4.0.1 규약과 본별 유도표를 코드 측에 단일 출처로 보유
2. **각도 → 라디안 변환의 단일 지점** — GeckoLib `GeoBone`에 값을 넣기 직전의 유일한 변환 경로

부호는 어디에서도 뒤집지 않는다. 이유는 4.0.1 하단 참조.

### 3.6 파라미터 노출 방식

**Forge Config (TOML) + 커맨드 직접 변경.** 둘 다 구현한다.

- TOML: `config/wardengirl-client.toml`. 파일 저장 후 커맨드로 리로드
- 커맨드: `/wardengirl param set <key> <value>` — 즉시 반영, 재접속 시 초기화

근거: 파라미터 30여 개를 각각 5회만 조정해도 150회 왕복이다. Java 상수로 가면 여기서 몇 시간이 소요된다. 초기 투자 30분으로 회수된다.

**Molang 수식 내부의 상수(호흡·바운스 등)는 json에 있으므로 F3+T로 즉시 반영된다.** TOML/커맨드는 Java 측 값(스프링 상수, 시선 감쇠, idle 간격 등)에 쓴다.

#### 3.6.1 프리셋 적용 대상 (T3에서 확정)

`/wardengirl param preset <min|low|default|high|max>` 는 기본값의 **×0.25 / ×0.5 / ×1 / ×2 / ×4** 등비 스윕이다. 목적은 하나다 — **"이 진폭이 자릿수가 맞나".**

> **프리셋은 진동 진폭에만 적용한다. 정적 오프셋과 비율 상수는 `param set` 으로 개별 조정한다.**

| 분류 | 프리셋 | 예 | 이유 |
|---|---|---|---|
| **진동 진폭** | **적용** | 호흡, 흔들림, 체중이동, 바운스, `headgear_amplitude`, `headgear_max_angle` | 자릿수를 묻는 값이다. 프리셋의 존재 이유 |
| 정적 자세 오프셋 | 제외 | `offset_arm_*_x`, `offset_leg_*_y`, `offset_head_x`, `offset_body_x` | **크기가 아니라 형태다.** 안짱 2°를 8°로 만드는 것은 진폭 탐색이 아니라 **다른 자세**를 만드는 것이고, 부작용으로 발끝 변위가 0.0987 → **0.3946px** 까지 올라가 접지가 깨진다 |
| 비율 상수 | 제외 | `headgear_stiffness`, `headgear_damping`, `headgear_asymmetry`, `look_gain` | 점화식의 비율이다. `DAMPING 0.35 → 1.4` 는 스프링을 4배 크게 만드는 것이 아니라 **발산시킨다**. `look_gain 1.0` 은 "엔티티가 실제로 보는 방향"이라 ×4에 의미가 없다 |
| **클램프 · 한계값** | **제외** | `look_yaw_max`, `look_pitch_max`, `headgear_max_angle` | **클램프는 안전장치다. 4배로 키우면 안전장치가 사라진다.** 실측에서 preset max 의 `head yRot` 이 `+83.869` 까지 갔다 — `LOOK_YAW_MAX 75 × 4 = 300` 이라 클램프가 아무것도 하지 않은 것이다 |
| 형태 | 제외 | `headgear_splay`, `headgear_tilt`, `headgear_pivot_x`, `headgear_pivot_y` | 정적 오프셋과 같다. 크기가 아니라 형태다 |

> **클램프와 한계값은 프리셋 대상이 아니다. 프리셋은 진동 진폭에만 적용한다.**
| 주기 | 적용 | `breath_period`, `sway_period`, `weight_shift_period`, `bounce_period` | "한 번에 몇 틱"도 자릿수를 묻는 값이다 |

제외는 **스윕에서의 제외**이지 튜닝에서의 제외가 아니다. 전부 `param set` 으로 개별 조정된다.

### 3.7 모델 규격

바닐라 알렉스 스킨 구조를 GeckoLib geo.json으로 재현한다.

| 파츠 | 크기(px) | 피벗 |
|---|---|---|
| **hip** | **큐브 없음** | **(0, 12, 0)** |
| head | 8×8×8 | (0, 24, 0) |
| body | 8×12×4 | **(0, 12, 0)** |
| arm_right | **3**×12×4 | (-5, 22, 0) |
| arm_left | **3**×12×4 | (5, 22, 0) |
| leg_right | 4×12×4 | **(-2.0, 12, 0)** |
| leg_left | 4×12×4 | **(2.0, 12, 0)** |

**팔 너비 3px (슬림).** 4px이면 클래식이 되어 컨셉이 무너진다.

**다리 피벗은 ±2.0이다.** 큐브도 피벗 중심으로 두어(`x = -4~0`, `0~4`) 두 다리가 정확히 맞닿는다. **피벗만 옮기면 겹침은 그대로 남는다** — 겹침을 만드는 것은 큐브 위치이기 때문이다. 근거는 Part 11.

**`hip`은 큐브가 없다.** 피벗만 존재하는 보이지 않는 본이며, 다리(`leg_right` / `leg_left`)와 `body`를 자식으로 갖는다. **`body` 피벗은 목(0, 24, 0)이 아니라 골반(0, 12, 0)이다** — 큐브 자체는 여전히 y 12~24를 차지한다. 근거는 Part 4.0 및 Part 11.

**headgear (워든 감각 촉수, sensory tendrils) — 좌우 분리:**

> **구판 폐기.** 구판은 "머리 위에 얹히는 좌우 한 쌍의 돌기, 각 2×5×2"였다. 그대로 만들면 **토끼귀**가 된다. 의도한 것은 워든의 감각 촉수이며, 머리 **위**가 아니라 머리 **양옆**에서 바깥 위로 뻗는 **얇은 평면**이다. 근거는 Part 11.

- `head`의 자식 **2개**: `headgear_right` / `headgear_left`
- 피벗: 머리 큐브 좌우 측면. 오른쪽 `(-4, 29, 0)`, 왼쪽 `(4, 29, 0)`
- 형태: **얇은 평면.** 큐브 크기 `3 × 13 × 0` + `inflate 0.02`
  - **크기는 geo.json 값이다. F3+T 로 즉시 반영된다.** 폭 `w` · 길이 `h` 를 바꾸면 `origin x = 피벗x − w/2` 를 함께 고친다 (평면을 피벗 위에 가운데 맞춤). 깊이는 0 을 유지한다 — 두께는 `inflate` 가 준다. **uv 는 손댈 필요가 없다** (면별 UV, 아래)
  - 두께 0 평면은 z-fighting이 나므로 inflate로 두께를 준다
  - 길이 13px > 머리 8px. 관성이 눈에 보이려면 머리보다 길어야 한다
  - 잔가지 없는 단순 형태. 워든 원본의 십자 구조는 쓰지 않는다
- **기본 각도와 부착 위치는 geo.json 에 없다. 파라미터다.** `geo.json` 은 모델 로드 시 한 번만 읽히므로 커맨드로 바꿀 수 없고, 형태를 확정하는 데 매번 재빌드·재캡처 왕복이 들었다. 아래 4개를 `param set` 으로 즉시 조정한다.

| 파라미터 | 기본 | 범위 | 의미 |
|---|---|---|---|
| `headgear_splay` | 30 | 0 ~ 90 | 바깥 각도. 0 = 수직, 90 = 수평 |
| `headgear_tilt` | 10 | −45 ~ 45 | 뒤로 젖힘. 양수 = 뒤로 |
| `headgear_pivot_x` | 4 | 0 ~ 8 | 부착 x (좌우 대칭). 4 = 머리 옆면 |
| `headgear_pivot_y` | 29 | 24 ~ 34 | 부착 y. 머리 큐브는 y24~32 |

  - 기본값에서 끝점은 피벗에서 `x ∓6.5`, `y +11.3` — 머리 옆으로 6.5px, 머리 위로 8.3px
  - 부호: `+zRot` 은 피벗 위의 점을 몹의 **왼쪽(+X)** 으로 보내므로 바깥은 오른쪽 촉수가 **음수**, 왼쪽이 양수다. `+xRot` 은 **뒤(−Z)** 로 보내므로 양수 tilt 가 뒤로 젖힘이다. 4.0.1 규약 그대로이며 어디에서도 뒤집지 않는다
  - **부착 위치는 본 이동(`position`)으로 구현한다.** 렌더가 `T(pos)·T(pivot)·R·T(-pivot)` 순서라 피벗 위의 뿌리 정점은 회전과 무관하게 `pivot + pos` 에 놓인다 — 즉 본을 옮기는 것은 피벗을 옮기는 것과 **정확히 등가**이고, 피벗과 달리 런타임에 바뀐다
  - **스프링은 이 값들에 영향받지 않는다.** 스프링은 `head` 회전을 쫓아 지연 오차를 내고, 기본 자세는 그 오차에 **더해질 뿐**이다. `splay` 를 바꿔도 점화식이 달라지지 않으므로 발산할 수 없다
- 텍스처: **`tendril.png` (별도 파일)**. 렌더 타입은 `GeoModel.getRenderType` 기본값 **`entityCutoutNoCull`** (4.8.4 바이트코드 확인) — 알파 컷아웃과 양면 렌더가 둘 다 필요한데 기본값이 이미 둘 다 만족한다
  - **UV 는 면별(`north`/`south`)이고 `uv_size` 가 선언 시트 크기(128)와 같다.** `GeoQuad.build` 가 UV 를 `texture_width/height` 로 나눠 정규화하므로, `uv_size = 128` 이면 정규화 결과가 `0~1` 이 되어 **바인딩된 텍스처 전체**를 샘플링한다. `tendril.png` 의 실제 픽셀 크기가 몇이든 맞고, 본체 시트에 자리를 예약할 필요도 없다
  - 왼쪽 본은 `uv_size` 의 u 성분이 **음수**다 — 같은 파일을 좌우 반전해 공용한다

**좌우를 왜 본 2개로 나누는가.** 스프링을 좌우 독립으로 돌려 위상을 미세하게 어긋나게 하기 위해서다. 본이 하나면 두 파츠가 완전히 같이 움직여 기계처럼 보인다. **단, 본만 나누는 것으로는 아무 효과가 없다** — 입력(head 회전)과 상수가 같으면 두 스프링의 출력은 비트 단위로 동일하다. 차이를 만드는 방법은 4.5.4 참조.

### 4.0 규약 (확정. 재검증 완료)

#### 4.0.1 회전 부호

기준점은 **피벗 바로 위의 점**. y축만 **피벗 바로 앞의 점**.

- `+xRot` : 기준점이 몹의 **뒤(-Z)** 로
- `+yRot` : 기준점(앞)이 몹의 **왼쪽(+X)** 으로 = 위에서 볼 때 반시계
- `+zRot` : 기준점이 몹의 **왼쪽(+X)** 으로

#### 4.0.2 본별 물리적 의미 (위에서 유도. 참조 전용)

| 본 | + | − |
|---|---|---|
| hip / body **xRot** | 뒤로 젖힘 | **앞으로 숙임** |
| hip / body **yRot** | 왼쪽 비틀기 | 오른쪽 비틀기 |
| hip / body **zRot** | 왼쪽 기울임 | 오른쪽 기울임 |
| head **xRot** | **위를 봄** | 아래를 봄 |
| head **yRot** | 왼쪽을 봄 | 오른쪽을 봄 |
| head **zRot** | 왼쪽 갸웃 | 오른쪽 갸웃 |
| arm / leg **xRot** | **앞으로** | 뒤로 |
| arm_right / leg_right **zRot** | 바깥으로 벌림 | 안쪽으로 붙임 |
| arm_left / leg_left **zRot** | 안쪽으로 붙임 | 바깥으로 벌림 |

> **좌우 zRot 부호가 반대다.** 대칭 동작은 반드시 좌우를 따로 적는다. `±` 표기 금지.

#### 4.0.3 각도 단위

문서의 모든 각도는 **도(degree)**. 라디안 변환은 `AxisConvention`의 단일 지점에서만. 부호는 어디서도 뒤집지 않는다.

#### 4.0.4 본 계층 (10개)

```
root                      위치 전용 (y, z 이동). 회전 미사용
└ hip                     전신 기울임 · 체중이동. 피벗 (0,12,0), 큐브 없음
  ├ body                  상체. 피벗 (0,12,0), 큐브 y12~24
  │ ├ head                피벗 (0,24,0)
  │ │ ├ headgear_right    감각 촉수. 물리 전용. 키프레임 금지
  │ │ └ headgear_left     감각 촉수. 물리 전용. 키프레임 금지
  │ ├ arm_right           피벗 (-5,22,0)
  │ └ arm_left            피벗 (5,22,0)
  ├ leg_right             피벗 (-2.0,12,0)
  └ leg_left              피벗 (2.0,12,0)
```

> 다리 피벗은 `±1.9`가 아니라 **`±2.0`**이다. `±1.9`는 큐브 좌우가 0.20px 겹쳐 안짱 오프셋에서 관통한다. 큐브 origin도 함께 옮겼다. 근거는 Part 11.

#### 4.0.5 hip vs body 사용 기준 (신설)

| 의도 | 본 |
|---|---|
| 상체만 숙이거나 젖힘 (호흡, 기지개, 축력) | **body** |
| 다리 포함 전신 기울기 (돌진, 착지 충격) | **hip** |
| 좌우 체중 이동 | **body** (구판 hip에서 이관) |
| 상체 좌우 흔들림 (미세 sway) | body |
| 전신 미세 비틀기 (yRot) | **body** (구판 hip에서 이관) |
| 전신 상하 이동 | **root.y** |
| 흉곽만 상승 | body.y |

**중요:** hip을 회전시키면 다리가 따라 돈다. 다리를 세워두려면 leg에 역회전을 넣어야 한다 (4.10.2 참조).

**정지 상태에서 hip을 회전시키지 않는다.** hip은 다리의 부모다. hip을 1도라도 돌리면 발 밑면이 **12px 레버** 끝에서 호를 그린다. `hip.zRot 0.8°`면 발끝 변위 **0.17px**이고, 이것은 각도 덤프에서 "규격 안"으로 보이면서 화면에서는 **발이 미끄러진다.** 각도로는 안 보이고 변위로만 보이는 결함이다.

- 정지 레이어(C1)에서 hip의 세 축은 **상수 0**이다.
- 상체 회전이 필요하면 body를 쓴다. body도 hip과 같은 `(0,12,0)`에서 피벗하지만 다리는 hip에 매달려 있으므로 body가 아무리 돌아도 발은 그 자리에 있다. (근거: `HIP3_body_Z` 캡처)
- hip에 키프레임이 들어가는 첫 동작은 **T9 대시**다. 발이 실제로 지면을 떠나거나 미끄러지는 것이 의도인 동작에 한한다.
- 검증: `/wardengirl trace`가 **발끝 변위**(발 밑면 중심의 x/z 이동량, px)를 상시 출력한다. 정지 자세 허용치는 **0.10px**이다.

### 원칙 1 — 운동연쇄

몸통에서 시작해 말단으로 전파. 각 본의 키프레임 시각을 지연만큼 뒤로 민다.

| 본 | 지연 |
|---|---|
| hip | 0 tick |
| body | +0.5 tick |
| leg | +0.5 tick |
| arm | +1.5 tick |
| head | +2 tick |
| headgear_right / headgear_left | 물리 자동 |

### 원칙 2 — 반대회전

`leg 양쪽 yRot = -body.yRot × 0.4`

머리는 시선 수평 유지 보정 (전정안반사):
`head.xRot 보정 = -body.xRot × 0.5`

> body가 **-x(앞으로 숙임)** 이면 head는 **+x(위를 봄)** 로 보정된다. 부호가 반대인지 반드시 확인할 것.

예외: 기본 공격에서 `head.yRot`은 body와 **같은 방향** (때리는 쪽을 봄).

### 원칙 3 — 무게중심 보상

- 팔을 앞으로 뻗음(+x) → `body.xRot`을 **+**(뒤로) 방향으로 (뻗은 각도 × 0.12)
- 한쪽 다리에 체중 → **`hip.zRot`** 을 그쪽으로, `head.zRot`을 반대로
- 앞으로 돌진 → `leg.xRot`을 **−**(뒤로)로 뻗어 지지

### 원칙 4 — 예비동작

모든 동작은 반대 방향으로 먼저 움직인다. 진폭 25%, 6틱 전.

### 원칙 5 — 오버슈트와 정착

배율 1.15~1.25배, 정착 4~6틱. 도달 `easeOutBack`, 정착 `easeOutSine`.

### 원칙 6 — 완전 정지 금지

C1은 꺼지지 않는다. 예외는 소닉붐 0~3틱뿐.

### 4.3 C1 상시 레이어 (Molang)

#### 4.3.1 호흡 (주기 60tick)

들숨에 흉곽이 오르고 상체가 살짝 젖혀지며, 머리는 수평을 유지하려 반대로 보정한다.

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| body | xRot | `0.5 * sin(t*6.0)` | 들숨에 뒤로 젖힘 |
| body | y | `0.12 * sin(t*6.0)` | 흉곽 상승 (px) |
| head | xRot | `-0.25 * sin((t - 2.0)*6.0)` | 수평 유지 보정 (2.0틱 지연 = -12°) |
| arm_right | zRot | `0.35 * (1 + sin((t - 1.5)*6.0))` | 바깥으로만. 범위 0 ~ +0.7 |
| arm_left | zRot | `-0.35 * (1 + sin((t - 1.5)*6.0))` | 바깥으로만. 범위 0 ~ -0.7 |

**다리는 호흡에서 뺀다.** (구판 `leg xRot -0.2` 삭제)

**`6.0 = 360/60`.** 구현에서는 주기(60틱)를 파라미터로 두고 `360/주기`로 환산한다 — 사람이 판단하는 단위는 "틱당 몇 도"가 아니라 "한 번에 몇 틱"이다.

**60틱 = 3초 = 분당 20회.** 사람 안정 시 호흡수에 해당한다. 30 → 44 → **60** 확정.

> **위상 지연은 도가 아니라 틱으로 적는다.** 구판은 44틱 기준으로 `-16°` / `-12°`였다. 지연을 도로 박아두면 주기를 바꾸는 순간 지연의 실제 길이가 같이 변한다 — 44틱의 `-16°`는 1.96틱이지만 60틱에서는 2.67틱이 되어, 주기만 늘렸는데 운동연쇄 지연까지 36% 늘어난다. 틱으로 적으면 주기와 무관하게 D틱이다. 환산: `-16° @44 → 1.96틱 → 2.0틱` (60틱에서 `-12°`), `-12° @44 → 1.47틱 → 1.5틱` (60틱에서 `-9°`). 원칙 1의 운동연쇄 지연도 틱 단위이므로 표기도 일치한다.

> **팔 zRot에 바깥 방향 바이어스를 건다.** 팔 안쪽면과 몸통 바깥면은 `x = ±4`로 **간격이 0**이라, 안쪽으로 가는 각도는 크기와 무관하게 즉시 관통한다. `(1 + sin)` 형태는 값을 `0 ~ 2×진폭`으로 만들어 **바깥으로만** 진동시킨다. 중립에서 시작해 벌어졌다 돌아오므로 "들숨에 어깨가 벌어진다"는 원래 의도도 유지된다. 계산 근거는 Part 11.

**[의도 크기]** 자세히 보면 알 정도. 시선을 끌면 과함.

> 구판 대비 변경: 주기 30 → **44틱**(분당 40회 → 27회), `body.xRot` 0.7 → 0.5, `head.xRot` 0.35 → 0.25, `arm zRot` 0.5 → 0.35(+바이어스), 다리 삭제. 30틱은 사람 안정 시 호흡의 3배 가까이 빨라 "까딱까딱"으로 읽혔다.

#### 4.3.2 바운스 (주기 25tick)

| 본 | 축 | 수식 |
|---|---|---|
| root | y | `0.4 * sin(t*7.2)` |

**순수 sin을 쓴다. `abs()`를 쓰지 않는다.**

절댓값은 바닥에서 튕기는 리듬을 만든다. 그 리듬은 "가만히 서 있는 존재"가 아니라 **"제자리 뛰기 하는 존재"**로 읽힌다 — 상시 레이어에는 부적합하다. `abs`를 빼면 실질 주기가 12.5틱에서 **25틱**으로 늘어나 느긋한 상하 호흡감이 된다.

접지 충격이 사라지므로 **다리 벌림(`leg zRot`)도 함께 폐기한다.** 흡수할 충격 자체가 없다.

**정지 상태 기본값은 `0.0`이다. 사용자 판정.** 서 있는 동료가 위아래로 통통거릴 이유가 없다.

**수식과 파라미터는 삭제하지 않고 남긴다.** T5 걷기에서 *이동 중* 바운스가 필요할 수 있다. "제거"가 아니라 "정지 상태에서만 0"이다.

**[의도 크기]** 정지 상태 `0.0` 확정.

#### 4.3.3 미세 흔들림 (주기 53tick)

호흡·바운스와 주기가 서로소에 가까워 위상이 계속 어긋난다. 반복 감지가 되지 않는 이유다.

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| body | zRot | `1.2 * sin(t*6.8)` | 상체 좌우 |
| head | zRot | `-0.7 * sin((t - 2.06)*6.8)` | 반대 보정 (2.06틱 지연 = -14°) |
| body | yRot | `0.5 * sin((t - 2.94)*6.8)` | 상체 미세 비틀기 (2.94틱 지연 = -20°) |

`6.8 = 360/53`. 구판 대비 진폭 상향(0.8→1.2, 0.5→0.7, 0.3→0.5). 호흡 진폭을 줄인 만큼 좌우 축의 비중을 키워 단일축 진자 인상을 깬다.

> 구판 오류 수정: `leg 양쪽 yRot -0.3`은 좌우 같은 부호여서 "발끝 안쪽"이 성립하지 않았다. 구 규약 기준으로도 모순이었다. yRot 비틀기로 대체. (감사 후보 B-5)
>
> **hip → body 이관.** 이 항의 yRot은 원래 `hip`이었다. hip은 다리의 부모라 0.5°만 돌아도 발이 12px 레버 끝에서 움직인다. 4.0.5 신설 조항에 따라 body로 옮겼다. 각도·주기·지연은 그대로다 — 바뀐 것은 **어느 본에 쓰느냐** 하나뿐이다.

#### 4.3.4 기본 자세 오프셋 (정적, 상시 가산)

비인간 실루엣의 절반이 여기서 나온다.

| 본 | 축 | 값 | 의도 |
|---|---|---|---|
| arm_right | **xRot** | **+4** | 힘 빼고 살짝 앞으로 |
| arm_left | **xRot** | **+4** | 힘 빼고 살짝 앞으로 |
| leg_right | yRot | **+2** | 안짱 (발끝이 +X로) |
| leg_left | yRot | **-2** | 안짱 (발끝이 -X로) |
| head | xRot | **-3** | 목 앞으로 |
| body | xRot | **-1.5** | 어깨 앞으로 |

> **팔은 zRot이 아니라 xRot이다.** 의도는 "좌우로 모은다"가 아니라 **"힘을 빼고 자연스럽게 늘어뜨린다"**이다. 사람이 편하게 설 때 팔은 좌우로 모이지 않고 살짝 앞으로 온다. `body.xRot -1.5`(어깨 앞으로)와도 이어진다.
>
> **기하학적으로도 zRot은 불가능하다.** 팔 안쪽면과 몸통 바깥면이 둘 다 `x = ±4`로 **맞닿아 있다**(간격 0). 안쪽으로 도는 zRot은 각도와 무관하게 즉시 몸통을 파고든다. `-4°`면 침투 **0.70px**이다. xRot은 앞뒤 회전이라 z평면에서 충돌할 대상이 없다. 계산 근거는 Part 11.

**[의도 크기]** 정지 상태에서 "사람 자세가 아니다"가 읽힐 정도. 과하면 구부정한 노인이 된다.

> **관통 2건 처리 완료.** 4.3.1 호흡 팔 zRot은 **바깥 방향 바이어스**로, 양다리 0.20px 겹침은 **피벗·큐브 ±2.0**으로 해결됐다. 남은 것은 안짱 오프셋의 모서리 스윕 **0.099px** 하나이며, 육안 식별 불가 수준으로 판단해 **감수한다.** 근거는 Part 11.

#### 4.3.5 체중 이동 (주기 79tick) — 신설

아주 느린 좌우 체중 이동이다. **세 번째 축이자 가장 느린 층.**

| 본 | 축 | 수식 | 의도 |
|---|---|---|---|
| body | zRot | `0.8 * sin(t*4.56)` | 좌우 체중 이동 (4.3.3 항에 **가산**) |
| head | zRot | `-0.4 * sin((t - 5.27)*4.56)` | 반대 보정 (5.27틱 지연 = -24°. 4.3.3 항에 **가산**) |

`4.56 = 360/79`.

**79는 60/53과 공배수가 사실상 없다.** LCM은 251,220틱 ≈ 209분이다. 세 주기가 절대 같은 조합으로 되돌아오지 않는다. **이것이 "규칙적 반복"을 깨는 핵심이며, 진폭이 아니라 위상 설계의 문제다.**

`head.zRot`은 4.3.3의 흔들림 보정과 이 항의 **합**이다. 덮어쓰지 않는다. **`body.zRot`도 마찬가지로 합이다** — 4.3.3의 `1.2`와 이 항의 `0.8`이 더해져 최대 **2.0°**에 달할 수 있다. 두 주기(53/79)가 어긋나므로 실제로 2.0°에 도달하는 순간은 드물다.

> **hip → body 이관.** 이 항의 zRot도 원래 `hip`이었다. 4.0.5 신설 조항 참조. 각도·주기·지연은 그대로다.

**[의도 크기]** 의식적으로 보이면 안 된다. "가만히 있는데 미묘하게 계속 다르다" 수준.

### 4.5 headgear 물리 (키프레임 금지)

#### 4.5.1 감쇠 스프링

각 축 독립. **단위는 도(degree).**

```
targetDeg   = head의 현재 각도 (도)
velocityDeg += (targetDeg - angleDeg) * STIFFNESS - velocityDeg * DAMPING
angleDeg    += velocityDeg
```

| 상수 | 값 |
|---|---|
| `STIFFNESS` | 0.25 |
| `DAMPING` | 0.35 |
| `AMPLITUDE` | 1.3 |
| `MAX_ANGLE` | **45** (도) |
| `ASYMMETRY` | 0.06 (좌우 강성 차) |

> **`MAX_ANGLE` 35 → 45.** 35에서는 기본 `AMPLITUDE 1.3`만으로 pitch 최대 스윙에서 `-33.197 ~ +34.390`까지 올라가 클램프에 닿았다. **클램프는 안전장치이지 상시 작동하는 제한이 아니다.** 35로 두면 `AMPLITUDE`를 조금만 올려도 즉시 붙어 장식이 뻣뻣해져 튜닝 여지가 사라진다.

**최종 적용:** `headgear.rotationDeg = clamp((angleDeg - targetDeg) * AMPLITUDE, ±MAX_ANGLE)`

> **차이값을 쓴다.** headgear는 head의 자식이라 head 회전은 이미 상속된다. 얹는 것은 지연 오차분뿐이다. 놓치면 장식이 두 배로 돈다.

`partialTick` 보간 필수.

#### 4.5.2 상태별 상수

| 상황 | STIFFNESS |
|---|---|
| 기본 | 0.25 |
| 소닉붐 축력 | 0.40 |
| 소닉붐 발포 | 0.15 |
| 돌진 중 | 0.18 |

**[의도 크기]** **T2/T3 튜닝 2순위.** 값에 매우 민감하다. 발산하면 DAMPING을 올린다.

#### 4.5.3 구현 규칙 (T3에서 확정)

**① 대입이다. 가산이 아니다.** 감각 촉수는 Part 10.4에 따라 애니메이션에 항목이 없다. 즉 다리에 쓴 해법(`rotation: [0,0,0]` 명시)을 쓸 수 없다. 누적을 막는 방법은 **매 프레임 절대값으로 덮어쓰는 것** 하나뿐이다.

`GeoBone` 의 setter 가 `markRotationAsChanged()` 를 호출하고 `AnimationProcessor` 가 그 본의 리셋을 영구히 건너뛰므로, `+=` 로 쓰면 다리와 정확히 같은 방식으로 누적된다. **대입이면 매 프레임 덮어써지므로 누적이 구조적으로 불가능하고, Part 10.4를 그대로 유지할 수 있다.** 구조 검사기가 촉수에 쓰는 `setRot*` 인자에 `getRot` 이 들어가지 않는지, 그리고 **좌우 두 본을 모두 도는지** 자동으로 확인한다. 한쪽만 쓰면 다른 쪽은 리셋도 덮어쓰기도 못 받는다.

**② 틱 단위로 적분한다.** 4.5.1의 점화식은 상수가 **틱당** 값이다. 프레임마다 돌리면 강성이 프레임률에 종속되어 200fps 기계에서 20fps 기계보다 10배 빨리 수렴한다 — 눈으로 한 튜닝이 다른 기계에서 무효가 된다. 엔티티의 틱 카운터가 올라갈 때만 적분하고, 렌더값은 마지막 두 틱 상태를 `partialTick` 으로 보간한다.

일시정지·포커스 상실 후의 밀린 틱은 **최대 20틱(1초)까지만** 따라잡는다. 그러지 않으면 1분 정지 후 1200회를 한 프레임에 돌려 스프링이 밀린 진동을 전부 울리고 도착한다.

**③ 엔티티별 상태다.** `GeoModel` 은 렌더러가 한 번만 만들어 화면의 모든 개체가 공유한다. 스프링 상태를 모델에 하나만 두면 서로 다른 방향을 보는 두 개체가 같은 장식 각도를 두고 다툰다. 엔티티 id 로 분리한다.

**④ 스폰 첫 프레임은 target 에 정착한 상태로 시작한다.** 0에서 출발하면 갓 소환된 몹이 장식을 한 번 크게 휘두르고 시작한다.

**⑤ 시선이 있어야 검증된다.** 스프링의 입력은 `head` 의 회전이다. 4.6 시선 가산이 없으면 입력이 호흡 `±0.25°` 뿐이라 스프링이 제대로 검증되지 않는다. 그래서 T3에서 4.6 가산을 함께 구현한다.

**⑥ 발산 후 복구 가드.** `|angle| > 1000°` 이거나 유한하지 않으면 상태를 버리고 target에 정착한 상태로 재시드한다. 근거는 Part 11 — 나쁜 값으로 한 번 발산시키면 값을 되돌려도 `|λ|=0.806/틱` 이라 정상 범위 복귀에 최대 **44초**가 걸리고, 그동안 장식이 클램프에 붙어 있어 "되돌려도 안 고쳐진다"는 잘못된 결론을 유도한다.

#### 4.5.5 다른 텍스처로 그리기 (T3 신설)

GeckoLib 은 모델당 텍스처 하나를 바인딩한다. 촉수를 별도 파일로 그리려면 **`GeoRenderLayer`** 를 쓴다 — 표준 방식이며 GeckoLib 자체도 `BoneFilterGeoLayer` 등을 이 형태로 제공한다.

호출 경로 (4.8.4 바이트코드):

```
renderRecursively
  ├ renderCubesOfBone(bone)                        ← 본의 큐브를 본체 텍스처로 그린다
  │    if (bone.isHidden()) return;                ← hidden 이면 여기서 건너뛴다
  ├ if (!isReRender) applyRenderLayersForBone(...) ← 레이어의 renderForBone 을 이 본에 대해 호출
  └ renderChildBones(...)
```

- **본마다, 그 본의 PoseStack 상태에서** 호출된다 — 스프링 회전이 이미 적용된 상태다
- **`applyRenderLayersForBone` 은 hidden 검사 바깥이다.** 따라서 촉수 본을 `setHidden(true)` 로 두면 본체 패스는 건너뛰고 레이어만 그린다 — 두 번 그려지는 것을 막는 방법이 이것이다
- 레이어 안에서는 잠시 `setHidden(false)` 로 두고 GeckoLib 의 큐브 루프(`renderCubesOfBone`)를 그대로 재사용한다. 큐브별 피벗·회전 처리를 직접 다시 쓰지 않기 위해서다

**스프링은 두 번 적분되지 않는다. 두 겹으로 보장된다.**

1. 레이어는 `handleAnimations` 를 호출하지 않는다. 스프링은 `setCustomAnimations` 에서 프레임당 한 번 돈다. 게다가 `applyRenderLayersForBone` 은 `if (!isReRender)` 안이라 레이어가 재귀하지도 않는다
2. 호출 그래프와 무관하게, `HeadgearSpring.advanceTo` 는 틱 카운터가 움직이지 않았으면 **0스텝**이다

#### 4.5.4 좌우 스프링 (T3 신설)

스프링 인스턴스를 **좌우 2개** 운용한다. `STIFFNESS` / `DAMPING` / `AMPLITUDE` / `MAX_ANGLE` 은 공유한다.

**본만 나누는 것으로는 아무 효과가 없다.** 두 스프링의 입력(`head` 회전)과 상수가 같으면 출력은 비트 단위로 동일하고, 두 촉수는 하나의 강체처럼 움직인다. 위상차를 만드는 방법이 있어야 분리가 의미를 갖는다.

**채택: 강성 비율 (`ASYMMETRY`).** 오른쪽 `STIFFNESS`, 왼쪽 `STIFFNESS × (1 - ASYMMETRY)`. 기본 `0.06`.

| 방식 | 장점 | 단점 |
|---|---|---|
| **A. 강성 비율 (채택)** | 정상상태 비용 0 — 양쪽이 같은 평형점에 수렴하고 과도응답만 다르다. 움직이는 동안 계속 어긋나고 멈추면 다시 일치한다 | 강성이 다르면 감쇠비도 미세하게 달라져 한쪽이 조금 더 출렁인다 |
| B. 초기 속도 차 | 구현이 가장 단순 | **21틱이면 사라진다.** 1% 감쇠 시간이 지나면 좌우가 완전히 동일해져 목적을 달성하지 못한다 |
| C. 입력 위상 지연 (왼쪽이 N틱 전 head 값을 본다) | 가장 "위상차"다운 방식. 지연량이 직관적 | head 회전 이력 버퍼가 필요하다. 정지 상태에서도 양쪽 평형점이 달라 촉수가 비뚤어진 채 멈춘다 |
| D. `AMPLITUDE` 좌우 차 | 구현 단순 | 위상이 아니라 **크기**가 달라진다. 살아있음이 아니라 좌우 비대칭 제작 결함으로 읽힌다 |
| E. 좌우 독립 미세 노이즈 | 완전 비주기 | 상태가 하나 더 늘고, 정지해도 멈추지 않는다 (4.5의 "정지 시 수렴"과 충돌) |

`ASYMMETRY = 0` 이면 좌우가 완전히 동일해진다 — 되돌리기 위한 값이다. 프리셋 스윕에서는 제외한다 (비율 상수).

`trace` 는 좌우를 각각 판정하고, **좌우 각도 최대치의 차이**를 출력한다. 이 값이 0이면 분리가 무의미하다는 뜻이므로 경고한다.

`current += (target - current) * DAMPING` (T4)

#### 4.6.1 방향값은 바닐라가 계산한다. 우리는 그리기만 한다

`LookAtPlayerGoal` · `RandomLookAroundGoal` 이 `yHeadRot` 을 움직이고, `LivingEntity.tickHeadTurn` 이 머리–몸통 차이가 50°를 넘으면 몸통을 강제로 돌리며 차이를 ±75°로 클램프한다. **이 거동은 재구현하지 않는다.**

GeckoLib 은 그 결과를 `EntityModelData(netHeadYaw, headPitch)` 로 넘겨주지만 **소비하는 코드가 없다.** `DefaultedEntityGeoModel` 하나만 이 데이터를 읽는데, 그 클래스는 `head.setRotX/setRotY` 로 **대입**하므로 C1 호흡 보정을 매 프레임 지운다. 그래서 상속하지 않는다.

**구현 방식(선택지 A): Java 가산.** `setCustomAnimations` 에서 4.3.4 정적 오프셋과 같은 방식으로 `head` 본에 **더한다.**

```
head.yRot += clamp(netHeadYaw * LOOK_GAIN, ±LOOK_YAW_MAX)
head.xRot += clamp(headPitch  * LOOK_GAIN, ±LOOK_PITCH_MAX)
```

부호를 뒤집지 않는다. GeckoLib 이 `EntityModelData` 를 만들 때 이미 `-netHeadYaw` / `-headPitch` 로 넣으므로(4.8.4 바이트코드 확인) 전달값은 이미 4.0.1 규약이다.

#### 4.6.2 상체 분배 폐기

> **구판 조항 삭제:** ~~"한계 초과 시 초과분을 `body.yRot`으로 넘긴다."~~

바닐라 `tickHeadTurn` 이 이미 50° 초과 시 `yBodyRot` 을 돌린다. 거기에 `body.yRot` 을 더 얹으면 **이중 회전**이다. 게다가 `yBodyRot` 은 PoseStack 레벨(모델 전체 회전)이고 `body.yRot` 은 본 레벨(상체만)이라, 겹치면 상체만 추가로 비틀린 어색한 자세가 된다.

**바닐라 거동을 그대로 쓰고 우리는 손대지 않는다.** `body.yRot` 은 4.3.3 미세 비틀기 `±0.5°` 전용으로 남는다.

#### 4.6.3 클램프 — 우리 클램프는 이중이 아니다

GeckoLib 이 `Mth.clamp(wrapDegrees(headYaw - bodyYaw), -85, 85)` 를 하기는 한다. **그러나 그 블록은 `shouldSit` 분기 안에 있어 서 있는 몹에서는 실행되지 않는다** (4.8.4 `actuallyRender` offset 115: `if (shouldSit == 0) goto 214`, 클램프는 128–212 구간). 서 있는 몹에 전달되는 값은 `yHeadRot - yBodyRot` **원값**이며 `wrapDegrees` 도 거치지 않는다.

실측 729표본 분포:

| 임계 | 초과 표본 | 비율 |
|---|---|---|
| \|netHeadYaw\| > 35° | 82 | 11.2% |
| > 50° | 65 | 8.9% |
| > 70° | 44 | **6.0%** |
| > 75° | 29 | 4.0% |
| > 85° | 6 | 0.8% |
| 최대 | **88.280°** | — |

유일한 상한은 바닐라 `getMaxHeadYRot()` = **75°** 이고, 렌더 시점 값은 머리와 몸통을 각각 `rotLerp` 한 차이라 회전 중 일시적으로 이를 넘는다(실측 88.28°).

**따라서 `LOOK_YAW_MAX = 70` 은 실제로 작동하는 클램프다.** 표본의 6.0%에서 걸리며, 걸리는 동안 머리는 70°에 멈춘 채 엔티티는 계속 도는 것으로 보인다. **이중 클램프가 아니다.**

- **슬림 모델 보정:** 팔 zRot 36까지 벌린다. 워든보다 크게 잡아야 빈약해 보이지 않는다
- 56틱 `head.xRot +8`로 플레이어를 올려다본다 — **원본에 없는 동료의 신호**

**[의도 크기]** 축력 팔 112°가 슬림 모델에서 빈약하면 130까지 올린다. **T8 튜닝 5순위.**

#### 4.9.3 떨림 오버레이 (10~38틱)

키프레임 값에 Molang으로 가산. 별도 레이어 불필요.

```
tremble = (0.3 + 2.2 * ((t - 10) / 28)) * sin(t * 86)
```

- 적용: `arm_R.xRot`, `arm_L.xRot`, `body.xRot`, `head.xRot`
- **팔에는 1.5배**
- 42~50틱 감쇠 잔진동: `1.2 * sin(t * 86) * (1 - (t-42)/8)`
- Molang `sin`은 도 입력이다 (4.0.3과 일치)

#### 4.9.4 필수 부수 처리

- **축력 중 이동속도 0 고정.** 접지 문제의 최대 완화책
- C1 호흡 유지. 0~3틱만 진폭 0
- headgear STIFFNESS 축력 0.40 → 발포 0.15

| root y | `0.3 * abs(sin(t*26))` | 낮고 빠른 바운스 |

## Part 6. 검증 체계

### 6.1 1차 검증의 성격

1차의 최종 판정자는 **사람의 눈**이다. 애니메이션 품질은 자동 검증되지 않는다.

그러나 커맨드는 필요하다. 목적이 다르다.

- **1차 커맨드의 목적:** 보고 싶은 순간을 즉시 만드는 것
- **2차 커맨드의 목적:** 기능이 작동했는지 값으로 판정하는 것

**1차 커맨드도 2차와 같은 원칙으로 만든다.** 2차에서 재작업하지 않기 위해서다.

### 6.2 가짜 검증 금지 — 두 원칙

#### 원칙 1: 상황을 실제로 조성한다

커맨드는 "지금 소닉붐 애니메이션 38틱 시점"을 **즉시 만들어야** 한다.

**금지:** 조건이 갖춰지길 기다리기. 상황을 흉내내는 로그만 출력하기. "재생을 요청했습니다"로 끝내기.

보고 싶은 시점에 즉각 그 시점을 만드는 것이 커맨드의 존재 이유다.

#### 원칙 2: 호출 성공을 성공으로 취급하지 않는다

커맨드가 오류 없이 실행됐다는 것은 **아무것도 증명하지 않는다.**

판정은 **결과의 변화, 변수의 변동**으로 한다.

- 애니메이션 상태가 실제로 시작됐는가 (`isActive`, 경과 틱 > 0)
- 경과 틱이 증가하고 있는가
- 대상 본의 회전값이 실제로 변했는가 (호출 전/후 비교)
- 파라미터를 바꿨으면 다음 프레임의 본 값이 달라졌는가

**커맨드는 이 값들을 출력해야 한다.** "성공"이라는 문자열만 출력하는 커맨드는 이 프로젝트에서 실패로 취급한다.

### 6.3 1차 필요 커맨드

| 커맨드 | 동작 | 출력 (필수) |
|---|---|---|
| `/wardengirl summon [pos]` | 즉시 소환 | 엔티티 UUID, 위치 |
| `/wardengirl axistest <bone>` | 본을 각 축 +10° 회전 후 정지 | 적용된 각도 3축 |
| `/wardengirl anim play <name>` | **조건 무시하고 즉시 재생** | 재생 전/후 컨트롤러 상태, 경과 틱 |
| `/wardengirl anim stop` | C3 초기화 | 정지된 컨트롤러명, 잔여 본 오프셋 |
| `/wardengirl anim freeze <tick>` | **지정 틱에서 고정** | 고정 틱, 그 시점 전 본의 회전값 8×3 |
| `/wardengirl anim step <n>` | freeze 상태에서 n틱 진행 | 진행 후 본 회전값 |
| `/wardengirl state` | 현재 상태 조회 | C1/C2/C3 각 재생명·경과틱, 본 10개 회전값, headgear 스프링 좌우 각도/속도, 시선 목표/현재 |
| `/wardengirl param list` | 파라미터 전체 | key = 현재값 (기본값 표시) |
| `/wardengirl param set <k> <v>` | 즉시 변경 | 변경 전값 → 후값, **다음 프레임 영향 본 값** |
| `/wardengirl param reload` | TOML 재로드 | 변경된 key 목록 |
| `/wardengirl ai <on\|off>` | 임시 AI 토글 (걷기 확인용) | 활성 Goal 목록 |
| `/wardengirl trace <ticks>` | **본 10개 × 3축 전 프레임 기록 + 자동 판정** | 축별 최소/최대, 기대 범위, OK / FAIL 범위이탈 / FAIL 단조누적 |

**`trace`는 T2에서 신설했다.** 정지 상태에서 다리가 계속 회전하는 버그가 한 태스크 주기 동안 발견되지 않았는데, 원인은 검증 덤프가 "이 레이어가 건드리는 본"만 찍고 있었고 다리가 거기 없었기 때문이다. **버그는 정확히 "움직일 리 없다"고 전제한 본에서 나온다.** 따라서 덤프를 전제에 맞춰 좁히면 그 덤프는 전제를 반증할 수 없게 된다.

`trace`는 **본 10개 × 3축을 무조건 전부** 기록하고, 각 축을 사양 범위와 대조해 자동 판정한다. 눈으로 표를 훑는 방식은 반복에 견디지 못한다.

- **CONST** — 정적 오프셋만 있는 본은 상수여야 한다
- **RANGE** — 진동하는 본은 (중심 ± 진폭) 안이어야 한다
- **FAIL 단조누적** — 창 전체에서 한 방향으로만 이동하면 누적이다. **단, 창이 해당 축의 주기보다 짧으면 판정을 보류한다** — 느린 사인파를 한 주기 미만으로 표본하면 정의상 단조롭기 때문이다(실제로 preset max에서 오탐이 났다). 바닐라 시선처럼 **주기가 아예 없는 축**은 판정을 보류하고 그 사실을 판정란에 표기한다 (묵시적 면제 금지)

#### 6.3.1 발끝 변위 (T2 신설, T3에서 사양 변경)

`trace` 는 매 프레임 `root → hip → leg` 순방향 운동학으로 발 밑면의 위치를 계산해 **최대 변위를 px 단위로** 출력한다. 정지 자세 허용치 **0.10px**.

**발끝 변위는 밑면 네 모서리의 최대 변위로 측정한다.** 중심점이 아니다.

밑면 **중심점**은 다리의 y 회전축 **위에** 있다. 따라서 `leg.yRot` 은 중심점을 정확히 0px 움직인다 — 안짱 오프셋 `±2°` 의 실측이 `0.0000px` 로 나오는데, 기하학적으로 옳지만 아무 정보도 주지 않는다. **화면에서 미끄러짐으로 읽히는 것은 모서리의 움직임이다.** 중심점만 보는 측정은 발의 모든 yaw 에 구조적으로 눈이 멀어 있고, T5 걷기는 다리를 y축으로 돌린다.

네 모서리를 전부 추적하고 **가장 큰 변위 하나**를 출력한다. 어느 모서리였는지 `FL / FR / BL / BR` 로 표기한다 (몹 기준: 앞 = +Z, 왼쪽 = +X).

접지 문제는 **각도로는 보이지 않고 변위로만 보인다.** `hip.zRot 0.8°` 는 각도 판정에서 범위 안이면서 발끝을 0.17px 움직였다 (Part 11). T5 걷기 · T8 소닉붐 · T9 대시에서 계속 쓴다.

#### 6.3.2 4.5 스프링 수렴 판정

`trace` 는 스프링의 **각도와 속도**를 본 값과 별도로 기록한다. 적용값은 지연 오차 `(angle − target) × AMPLITUDE` 이므로, **움직이는 머리를 쫓으며 진폭이 커지는 스프링도 본 값은 클램프 안에 있을 수 있다.**

**판정은 표본이 아니라 해석으로 한다.** 이 점화식은 선형계이고, 안정성은 입력과 무관하게 `STIFFNESS`(k) · `DAMPING`(c) 만의 함수다. `e = angle − target` 으로 두면

```
v' = (1-c)·v - k·e
e' = (1-c)·v + (1-k)·e        →   λ² - (2-c-k)λ + (1-c) = 0
```

두 근이 모두 단위원 안에 있을 Jury 조건은 **`k > 0`, `k < 4 - 2c`, `0 < c < 2`** 로 환원된다. 사양값 `k=0.25, c=0.35` 에서 판별식 `-0.64 < 0` (감쇠진동), `|λ| = 0.8062`, 주기 `12.1틱`, 1%까지 `21.4틱`.

실측 각도·속도와 **입력폭 대비 초과폭**은 계속 출력하되 **참고값**이다. 초과폭은 사람이 눈으로 튜닝하는 값("지나쳤다 되돌아오는가")이지 자동 판정 대상이 아니다.

> **구판 판정 기준 폐기.** 초판은 "창 마지막 1/4의 최대 |속도| 가 첫 1/4의 4배를 넘으면 발산"이었다. **4회 중 3회 오탐이 났다.** 스프링은 바닐라 시선이라는 **랜덤 타이머 입력에 구동되는 계**이므로, 앞이 조용하고 뒤에 큰 회전이 오면 비율이 ∞ 가 된다. "속도가 커졌다"는 입력을 측정한 것이지 스프링을 측정한 것이 아니다. 단조누적 오탐과 같은 종류의 결함이다 — **구동계에 대해 구간 비교를 판정으로 쓰지 않는다.**

**`anim freeze` + `state`가 1차의 핵심 도구다.** 축력 최고점이나 발포 순간의 포즈를 정지 상태로 관찰할 수 있어야, 흐르는 동작에서 놓치는 문제를 잡을 수 있다.

### 6.4 사람 ↔ 구현자 피드백 프로토콜

애니메이션 피드백의 정확도 순서:

1. **최선:** GIF 또는 짧은 영상
2. **좋음:** `anim freeze` 후 특정 틱의 스크린샷
3. **가능:** "몇 틱에서 무엇이 어떻게" 형태의 구체적 서술
4. **비효율:** "부자연스럽다", "어색하다" 등 총평만

**구현자는 총평만 받았을 때 임의 수정하지 않고, 어느 틱의 어느 본이 문제인지 질문한다.**

### 2026-07-27 (2차 개정, 폐기됨) — Part 4.0 각도 부호 규약: 말단 기준안

**변경.** 본별 상대 표현 표(`arm +zRot = 안쪽`, `leg +zRot = 벌림` 등)를 폐기하고, 시점 무관·월드 절대 기준의 단일 규약으로 교체(4.0.1).

```
+xRot : 본의 말단이 몹의 뒤쪽으로 이동
+yRot : 위에서 내려다볼 때 시계방향
+zRot : 본의 말단이 몹의 오른쪽(-X)으로 이동
```

**근거 — 규약 자체의 결함.** 구 규약은 팔과 다리에 정반대 의미를 부여했다(`arm +zRot = 몸 안쪽으로 붙임` vs `leg +zRot = 벌림`). 또한 "안쪽"은 좌우가 서로 반대 방향이라 **단일 부호로 표현이 불가능**하다. 실제로 4.3.4가 `arm_right +4` / `arm_left -4`를 둘 다 "안쪽"이라 적어 규약 표와 모순됐다. 부호 반전 상수만으로는 해결되지 않는 종류의 결함이므로 규약을 재정의했다.

**근거 — T1 1순위 축 검증 결과.** `/wardengirl axistest <bone> <axis> ±45`로 측정, 시점 `side_nx`(월드 -X에서 +X를 봄, 화면 오른쪽 = 몹 정면 +Z) 및 `front`(월드 +Z에서 -Z를 봄) 고정 캡처를 사람이 판정.

| 캡처 | 구 규약 기대 | 실제 관측 | 판정 |
|---|---|---|---|
| `P1_arm_right_X` | 뒤로 젖힘 | 앞으로 | 불일치 |
| `P1_leg_right_X` | 뒤로 뻗음 | 앞으로 | 불일치 |
| `P1_arm_right_Z` | 몸 안쪽으로 붙임 | 바깥으로 | 불일치 |

**부수 확정.** `arm_right` / `leg_right`가 월드 -X에 위치하는 것은 정상이다. 몹이 +Z를 향하면 그 몹의 오른손은 -X를 가리킨다. 명명 오류가 아니다.

```
arm_left  zRot = -0.35 * (1 + sin(t*8.2 - 12))   → 범위 0 ~ -0.70  (전부 바깥)
```

preset max(×4)에서도 범위는 `0 ~ ±2.80`으로 **안쪽 성분이 0**이다. 관통이 원천 차단된다.

#### (4) 다리 피벗 ±1.9 → ±2.0

**변경.** `leg_right` 피벗 `(-1.9,12,0)` → `(-2.0,12,0)`, 큐브 `x=[-3.9,0.1]` → `[-4.0,0.0]`. `leg_left` 대칭. 겹침 `0.20px` → **`0.00px`**.

**피벗만 옮기면 겹침은 그대로 남는다.** 겹침을 만드는 것은 큐브 위치이므로 큐브도 함께 옮겼다.

> **정정 — 구현자의 이전 보고 오류.** 이전 보고에서 "바닐라는 ±2를 써서 정확히 맞닿는다"고 했으나 **사실이 아니다.** 1.20.1 `HumanoidModel` 바이트코드 확인 결과 `left_leg`는 `addBox(-2,0,-2, 4,12,4)` + `PartPose.offset(1.9, 12, 0)`으로, **바닐라에도 동일한 0.2px 겹침이 있다.** 즉 초안의 ±1.9는 바닐라 정확값이었고, 이번 ±2.0 변경은 바닐라 복원이 아니라 **바닐라와 0.2px 다르게 만드는 의도적 개선**이다(다리 폭 총 7.8px → 8.0px). 겹침 제거라는 목적은 달성되므로 변경은 유지하되, 근거를 정정해 기록한다.

**남은 관통 1건은 감수한다.** 안짱 오프셋 `leg yRot ±2°`의 모서리 스윕 `0.099px`. 육안 식별 불가 수준. 보이면 그때 처리한다.

### 2026-07-27 — 버그 수정: 정지 상태에서 다리가 계속 회전

**증상.** 정지 상태에서 양다리가 y축으로 멈추지 않고 회전했다.

**원인 — 값으로 특정했다.** 4.3.4 정적 오프셋이 대입이 아니라 **매 프레임 가산**되고 있었다.

바이트코드 확인 결과:
- `GeoBone.setRotY(float)`는 내부에서 **`markRotationAsChanged()`를 호출한다.**
- `AnimationProcessor`는 `hasRotationChanged()`가 참인 본의 **리셋을 건너뛴다.**

따라서 Java 오프셋 쓰기가 **스스로 "변경됨" 표시를 남겨**, 두 번째 프레임부터 그 본은 영원히 리셋되지 않고 `+=`가 누적된다. 프레임당 +2°는 초당 100°를 넘는다.

**`body`/`head`/`arm`/`hip`이 무사했던 이유.** 이들은 `animation.json`이 `rotation: [x, y, z]` **3축 전부를 매 프레임 절대값으로** 덮어쓴다. `arm`의 `xRot`처럼 수식이 `0`인 축도 명시적으로 0이 쓰인다. **json에 항목이 아예 없던 `leg`만** 리셋도 덮어쓰기도 받지 못해 누적됐다.

**수정.** `animation.json`에 `leg_right` / `leg_left`의 `rotation: [0, 0, 0]`을 명시했다. 매 프레임 절대값으로 덮어써지므로 누적이 구조적으로 불가능해진다.

**규칙으로 승격.** *Java 정적 오프셋을 받는 본은 반드시 애니메이션에 `rotation` 채널을 가져야 한다.* 자동 검사에 넣어 재발을 막는다.

**검증 절차의 결함이 더 근본 원인이다.** 직전 보고의 실측 표에 `leg`가 하나도 없었다. "이 레이어는 이 본만 쓴다"는 전제로 덤프를 좁혔고, 버그는 정확히 그 전제가 깨진 곳에 있었다. **덤프를 전제에 맞춰 좁히면 그 덤프는 전제를 반증할 수 없다.** 대응으로 `/wardengirl trace`를 신설했다(Part 6.3).

**부수 발견 — 검사기 자체의 오탐.** 단조 판정이 preset max에서 `hip.zRot`을 FAIL로 잡았다. preset은 주기도 ×4 하므로 체중이동 주기가 79 → **316틱**이 되는데 추적 창은 300틱이었다. 한 주기보다 짧은 창에서 사인파는 정의상 단조롭다. **창이 주기보다 짧으면 누적 판정을 보류**하도록 고쳤다.

**수정 후 실측 (300틱 / preset max는 700틱, 본 9개 × 3축 = 27항목).**

```
leg_right  yRot   +2.000  ~  +2.000   CONST +2.000 고정   OK
leg_left   yRot   -2.000  ~  -2.000   CONST -2.000 고정   OK
leg_*      xRot,zRot        0 고정                        OK
preset max: leg_right yRot +8.000 고정 / leg_left -8.000 고정   OK
```
기본·preset max 두 조건 모두 **27항목 전부 통과.**

### 2026-07-27 — hip 회전 폐지: 발끝이 12px 레버 끝에서 움직인다

**증상.** 정지 상태에서 발이 미끄러지듯 보였다. 각도 덤프는 전 항목 통과였다.

**각도로는 보이지 않는 결함이다.** `hip`은 다리의 부모이므로 hip이 회전하면 다리 전체가 따라 돈다. 발 밑면은 hip 피벗 `(0,12,0)`에서 **12px 아래**에 있다. 레버가 12px이므로:

| hip 회전 | 발끝 수평 변위 |
|---|---|
| `zRot 0.8°` (4.3.5 체중이동) | `12 × sin(0.8°)` = **0.168px** |
| `yRot 0.5°` (4.3.3 비틀기) | 피벗에서 2px 떨어진 다리 기준 `2 × sin(0.5°)` = 0.017px |
| preset max (`zRot 3.2°`) | `12 × sin(3.2°)` = **0.670px** |

0.168px는 27항목 판정에서 `hip zRot ±0.8` 범위 안이라 **OK로 나온다.** 판정 기준이 각도뿐이었기 때문에 통과했다. 접지 문제는 각도가 아니라 **변위**로만 드러난다.

**수정 — hip의 회전을 전부 body로 옮겼다.**

| 구판 | 신판 |
|---|---|
| `hip.yRot = 0.5 * sin(...)` | `body.yRot = 0.5 * sin(...)` |
| `hip.zRot = 0.8 * sin(...)` | `body.zRot += 0.8 * sin(...)` |
| — | `hip.rotation = [0, 0, 0]` (상수) |

**body로 옮기면 왜 해결되는가.** body도 hip과 같은 `(0,12,0)`에서 피벗한다. 즉 **상체가 도는 모습은 완전히 같다.** 다른 것은 계층뿐이다 — 다리는 `hip`의 자식이지 `body`의 자식이 아니므로, body가 아무리 돌아도 다리는 그 자리에 남는다. `HIP3_body_Z` 캡처에서 확인된 성질이다. 각도·주기·위상 지연은 하나도 바꾸지 않았다.

`body.zRot`은 이제 4.3.3 흔들림(`1.2`)과 4.3.5 체중이동(`0.8`)의 **합**이며 이론상 최대 `2.0°`다. 주기가 53/79로 어긋나므로 실제 도달은 드물다. 과해 보이면 사용자 판정으로 낮춘다.

**4.0.5에 조항을 신설했다.** *정지 상태에서 hip을 회전시키지 않는다.* hip에 키프레임이 들어가는 첫 동작은 T9 대시다.

**검증 절차에 항구적으로 추가 — 발끝 변위.** `/wardengirl trace`가 `root → hip → leg` 순방향 운동학으로 **발 밑면 중심의 x/y/z 이동량**을 매 프레임 계산해 최대 변위를 px로 출력한다. 정지 자세 허용치 `0.10px`. T5 걷기 · T8 소닉붐 · T9 대시에서 계속 쓴다. 각도만 보는 판정은 접지 문제를 구조적으로 놓친다.

**자동 검사 추가.** `vital.hip.rotation == [0,0,0]`을 구조 검사기에 넣었다. 규칙을 기억에 의존시키지 않는다.

**위치 덤프의 좁힘도 함께 제거했다.** 위치 실측이 `root`/`body` 두 본만 읽고 있었다 — "위치를 쓰는 본은 이 둘뿐"이라는 전제였고, 이것은 다리 회전 버그를 통과시킨 것과 **같은 종류의 좁힘**이다. 회전과 마찬가지로 **본 9개 전부**를 읽도록 고쳤다.

### 2026-07-27 — 사전 조사: 바닐라 시선은 지워진 것이 아니라 연결된 적이 없었다

**우려.** `animation.json` 이 `head` / `body` 의 rotation 3축을 매 프레임 절대값으로 덮어쓰므로, 바닐라가 계산한 `yHeadRot` / `yBodyRot` 이 여기서 지워질 수 있다. 사실이라면 T4에서 발견될 때 T3 작업을 되돌려야 한다.

**결과 — 덮어쓰기가 아니라 미연결이었다.** 원인이 다르므로 대응도 다르다.

바이트코드(GeckoLib 4.8.4):

| 값 | 어디로 가는가 | 본을 건드리는가 |
|---|---|---|
| `yBodyRot` | `GeoEntityRenderer.applyRotations` → `poseStack.mulPose(Axis.YP.rotationDegrees(180 - bodyYaw))` | **아니오.** PoseStack 레벨, 본 트리 바깥 |

### 2026-07-27 — 4.6 상체 분배 폐기, 클램프는 이중이 아님을 확인

**상체 분배 삭제.** 구판 4.6의 "한계 초과 시 초과분을 `body.yRot` 으로 넘긴다"를 삭제했다. 바닐라 `tickHeadTurn` 이 이미 50° 초과 시 `yBodyRot` 을 돌리므로 이중 회전이고, 두 값은 층이 달라(PoseStack vs 본) 겹치면 상체만 추가로 비틀린 자세가 된다.

### 2026-07-27 — T3: headgear 스프링 + 시선 가산 + AI Goal 정식 활성화

### 2026-07-27 — 검사기 오탐 2건째: 구동계에 구간 비교를 쓰면 안 된다

**증상.** T3 스프링 수렴 판정이 4회 중 3회 `FAIL 발산` 을 냈다.

```
스프링 y축  각도 -81.336 ~ +80.074   속도 -14.091 ~ +12.790
            |속도| 초반 0.000 → 후반 14.091 (×Infinity)   FAIL 발산
```

**스프링이 아니라 판정 기준이 틀렸다.** 초판 기준은 "창 마지막 1/4의 최대 |속도| 가 첫 1/4의 4배를 넘으면 발산"이었는데, 이 스프링의 입력은 **랜덤 타이머로 도는 바닐라 시선**이다. 창의 앞이 조용하고 뒤에 큰 회전이 오면 비율이 ∞ 가 된다. 스프링은 해야 할 일을 정확히 했다.

**교체: 해석적 판정.** 점화식이 선형계이므로 안정성은 입력과 무관하게 `k`·`c` 만의 함수다. Jury 조건 `k > 0`, `k < 4-2c`, `0 < c < 2` 를 직접 검사한다 (Part 6.3.2). 사양값에서 `|λ| = 0.8062`, 감쇠진동 주기 12.1틱, 1%까지 21.4틱. 창 안에서 머리가 무엇을 했든 결과가 바뀌지 않는다.

**규칙으로 승격.** *구동계(외부 입력에 끌려가는 계)에 대해 구간 비교를 자동 판정으로 쓰지 않는다.* 앞선 단조누적 오탐(창 < 주기)과 같은 종류의 결함이다 — 둘 다 **표본 구간의 우연한 성질을 계의 성질로 착각**했다.

**판정기 자체의 검사도 추가했다.** 검증 하네스에서 `headgear_damping = 2.5` 로 Jury 조건을 일부러 위반시켜 판정기가 실제로 `FAIL` 을 내는지 확인한다. 통과만 확인하는 검사는 고장난 검사와 구분되지 않는다.

### 2026-07-27 — headgear를 토끼귀로 잘못 기술. 워든 감각 촉수로 교체하고 좌우 본 분리

**사양 오류.** Part 3.7에 headgear를 "머리 위에 얹히는 좌우 한 쌍의 돌기, 각 2×5×2"로 적었다. 그대로 만들면 **토끼귀**가 된다. 의도한 것은 워든의 **감각 촉수(sensory tendrils)** 이며, 머리 **위**가 아니라 머리 **양옆**에서 바깥 위로 뻗는 **얇은 평면**이다.

| 항목 | 구판 | 신판 |
|---|---|---|
| 본 | `headgear` 1개 | `headgear_right` / `headgear_left` **2개** |

### 2026-07-27 — 미결 판정 반영: 클램프 2건과 프리셋 범위

### 2026-07-27 — 촉수 형태를 파라미터로 이관, 클램프를 프리셋에서 제외

**형태를 두 번 고쳤고 매번 재빌드·재캡처 왕복이 들었다.** `geo.json` 은 모델 로드 시 한 번만 읽히므로 큐브 `rotation` 에 굽어 있는 각도는 커맨드로 바꿀 수 없다. 필요한 것은 구현자가 값을 잘 추측하는 것이 아니라 **사람이 게임 안에서 빠르게 훑는 것**이다.

**4개 전부 런타임으로 열렸다.**

| 파라미터 | 기본 | 범위 | 구현 |
|---|---|---|---|
| `headgear_splay` | 30 | 0 ~ 90 | 본 `zRot` (좌우 부호 반대) |
| `headgear_tilt` | 10 | −45 ~ 45 | 본 `xRot` |
| `headgear_pivot_x` | 4 | 0 ~ 8 | 본 `position` |
| `headgear_pivot_y` | 29 | 24 ~ 34 | 본 `position` |

**피벗이 열린 이유.** `CoreGeoBone.setPivotX/Y/Z` 는 존재하지만 큐브 정점이 이미 구워져 있어 **회전 중심만 바뀔 뿐 부착점 이동이 아니다** (회전이 0이면 아무 변화도 없다). 대신 **본 이동**을 쓴다. 렌더는 `T(pos)·T(pivot)·R·T(-pivot)` 순서이므로 피벗 위의 뿌리 정점은 `T(-pivot)` 으로 원점에 가고, 회전해도 원점이고, 되돌아와 **`pivot + pos`** 에 놓인다 — **회전과 무관하게** 그렇다. 즉 본을 옮기는 것은 피벗을 옮기는 것과 **정확히 등가**이며, 피벗과 달리 런타임에 바뀐다. F3+T 도 필요 없다.

x 부호는 `AxisConvention.setPositionPx` 한 곳에서만 뒤집는다 — `translateMatrixToBone` 이 `translate(-posX/16, +posY/16, +posZ/16)` 인데 `translateToPivotPoint` 는 `+pivotX` 라, 본 position x 만 이 프로젝트의 다른 모든 x 와 반대다 (4.8.4 바이트코드). `toRad` 와 같은 이유로 단일 지점이다.

**스프링은 이 값들에 구조적으로 영향받지 않는다.** 스프링은 `head` 회전을 쫓아 지연 오차를 내고, 기본 자세는 그 오차에 **더해질 뿐**이다. 점화식의 상태·상수·입력 어디에도 `splay` 가 들어가지 않으므로 발산할 수 없다. 추론이 아니라 구조다.

**크기는 여전히 `geo.json` 이다** (F3+T). 큐브 정점 자체를 바꾸는 일이라 본 변환으로는 못 한다. 편집 규칙을 geo.json 주석과 Part 3.7 에 적었다 — 폭 `w` 를 바꾸면 `origin x = 피벗x − w/2` 와 uv 영역 `2w × h` 를 함께 고쳐야 한다.

**클램프 3개를 프리셋 스윕에서 제외했다.** `look_yaw_max` / `look_pitch_max` / `headgear_max_angle`. 클램프는 안전장치이고 4배로 키우면 안전장치가 사라진다 — 실측에서 preset max 의 `head yRot` 이 `+83.869` 까지 갔는데, `75 × 4 = 300` 이라 클램프가 아무것도 하지 않은 것이다. `damping` 을 뺀 것과 같은 이유다.

프리셋 스윕 대상은 **15개**로 줄었다: 호흡 5 · 바운스 2 · 흔들림 4 · 체중이동 3 · `headgear_amplitude` 1.

**파라미터에 명시 범위를 도입했다.** 구판은 기본값의 ×0.01 ~ ×10 을 자동 유도했는데, 피벗 좌표 29 에 대해 `0.29 ~ 290` 은 아무도 훑지 않는 범위다. 형태 파라미터는 설계가 인정하는 범위를 직접 들고 있고 TOML 도 그 범위로 정의된다.

### 2026-07-27 — 텍스처 2종 적용, 촉수 형태 정정

**텍스처가 두 파일로 나뉜다.** 본체 `warden_girl.png` 128×128(표준 알렉스 레이아웃 2배)과 촉수 전용 `tendril.png` 10×10. 촉수를 별도로 두는 이유는 스킨과 독립적으로 다시 그리기 위해서다.

본체 UV 는 레이아웃이 표준 그대로라 **픽셀값을 2배 하고 `texture_width/height` 를 128 로 올리면 끝**이다: head `(0,0)`, body `(32,32)`, arm_right `(80,32)`, arm_left `(64,96)`, leg_right `(0,32)`, leg_left `(32,96)`.

**촉수는 렌더 레이어로 그린다** (4.5.5). GeckoLib 은 모델당 텍스처 하나를 바인딩하므로 두 번째 텍스처에는 `GeoRenderLayer` 가 필요하다. 세 가지를 바이트코드로 확인하고 구현했다.

1. `GeoRenderLayer.renderForBone` 이 `renderRecursively` 안에서 **본마다** 호출된다 — 그 본의 PoseStack 상태, 즉 스프링 회전이 적용된 상태다
2. **이중 적분 없음.** 레이어는 `handleAnimations` 를 부르지 않고, `applyRenderLayersForBone` 은 `if (!isReRender)` 안이라 재귀하지도 않는다. 독립적으로, `advanceTo` 는 틱이 안 움직였으면 0스텝이다
3. **본체 패스에서 제외 가능.** `renderCubesOfBone` 은 `isHidden()` 이면 즉시 반환하지만 `applyRenderLayersForBone` 은 그 검사 **바깥**이다. 촉수를 매 프레임 `setHidden(true)` 로 두면 본체는 건너뛰고 레이어만 그린다

**면별 UV 로 별도 파일을 맞춘다.** `GeoQuad.build` 가 UV 를 `texture_width/height` 로 나눠 정규화하므로, `north`/`south` 면에 `uv_size = [128,128]`(= 선언 시트 크기)을 주면 정규화 결과가 `0~1` 이 되어 **바인딩된 텍스처 전체**를 샘플링한다. `tendril.png` 의 실제 픽셀 크기와 무관하고, 본체 시트에 자리를 예약할 필요도 없다. 왼쪽 본은 `uv_size` 의 u 가 음수라 같은 파일을 좌우 반전해 공용한다.

**형태 정정 (사용자 판정).** 13px / 30° 는 과했다. 워든 원본은 훨씬 짧고 얌전하다.

### 2026-07-27 — 검사기 오탐 3건째: 기대 범위가 모델링하지 않은 값을 재고 있었다

**증상.** 형태 파라미터를 흔드는 검증에서 촉수 본 `zRot` 이 `-90.168` 까지 가 `실패 2개` 가 났다.

**앞선 두 오탐과 같은 계열이다.** ①창이 주기보다 짧은데 단조를 누적으로 판정 ②구동계에 구간 비교를 적용 ③기대 범위가 실제 계산식을 반영하지 않음. 셋 다 **검사 대상의 구성을 검사기가 정확히 알고 있지 않아서** 났다. 기대값은 코드의 실제 계산식에서 유도해야 하며, 기억으로 적으면 어긋난다.

### 2026-07-27 — 촉수를 스킨에 통합. 전용 렌더 레이어 폐기

**폐기 이유.** `reRender` 경로는 상태가 옳은데도 아무것도 그려지지 않았고, 그 앞에 `renderForBone` 경로는 **촉수 다음에 방문하는 본을 전부 망가뜨렸다.** 원인은 `MultiBufferSource.BufferSource.getBuffer` 다 — 모델 도중에 두 번째 `RenderType` 을 요청받으면 진행 중이던 배치를 끝내는데, `renderRecursively` 는 시작할 때 받은 `VertexConsumer` 에 계속 쓴다. 그래서 팔과 다리가 촉수 배치로 들어가 촉수 텍스처로 그려졌다.

**텍스처 하나 · 버퍼 하나 · 패스 하나면 이 실패는 재현될 수 없다.** 고치는 대신 없앴다.

**UV.** 촉수를 `warden_girl.png` 안 UV `(54,16)-(64,26)` 에 그려 넣었다. 128px 파일이므로 실제 파일 픽셀로는 `(108,32)-(128,52)` 다.

```
headgear_right  north uv [54,16]  uv_size [ 10,10]
headgear_left   north uv [64,16]  uv_size [-10,10]     (좌우 미러)
south           uv [4,4]  uv_size [1,1]                (면 제거)
```

**박스 UV 는 자리가 없었다.** 큐브의 박스 UV 직사각형은 `2(w+d) × (d+h)` 라 10×10×0 평면이면 `20×10` 인데, 64 공간에 그만한 빈 자리가 **0곳**이다. 면별 UV 를 쓰면 그리는 면 하나만 `10×10` 을 차지하고, 그 크기의 빈 자리는 23곳 있었다.

**팔 UV 직사각형은 14폭이지 16폭이 아니다.** 슬림 팔은 `w=3, d=4` 이므로 `2(3+4)=14`. `(40,16)-(54,32)` 에서 끝나기 때문에 촉수 블록 `(54,16)` 과 겹치지 않는다. 16으로 잡으면 겹치는 것처럼 보인다.

**south 면의 `uv [0,0]` 은 이 시트에서 쓸 수 없다.** 파일 픽셀 `(0,0)` 이 불투명 살색 `(252,228,211,255)` 이다. `tendril.png` 에서는 투명이었지만 스킨 시트에서는 아니다 — 그대로 뒀으면 촉수 뒷면마다 살색 사각형이 그려진다. `(4,4)` 로 옮겼다. 머리 base 빈 모서리 한가운데로 자신과 이웃이 모두 알파 0 이다.

### 2026-07-27 — 렌더 타입 `entityCutoutNoCull` → `entityTranslucent`

**이유.** 스킨에 **의도된 반투명 픽셀 47개**가 있다 (알파 12/16/129/160/177/240). `entityCutoutNoCull` 은 `a < 0.1` 만 버리고 나머지를 불투명으로 그려 이 값들을 전부 무시한다.

**양면 렌더는 유지된다 — 바이트코드로 확인.** 깊이 0 평면이라 뒤에서도 보여야 하는데, 두 타입 모두 컬 셰이드가 같은 필드다.

```
RenderType.entityTranslucent   -> setCullState(RenderStateShard.f_110110_)
RenderType.entityCutoutNoCull  -> setCullState(RenderStateShard.f_110110_)
f_110110_ = new CullStateShard(false)  -> setup 에서 RenderSystem.disableCull()
빌더 기본값 f_110158_ = CullStateShard(true) -> 아무것도 하지 않음 (GL 기본 컬링 유지)
```

`entity_translucent_cull` 이 **별도 타입으로 존재하고 `setCullState` 를 호출하지 않는다**(= 기본값 CULL)는 것이 방증이다.

**실측으로 블렌딩을 확인했다.** 화면 y=412 픽셀:

```
측정 (116,158,158)
= 0.710 x [ 0.694 x (211,255,255)재킷 + 0.306 x (56,149,147)안쪽 ]
예측 (116.2, 158.1, 157.7)   잔차 0.40
cutout 이었다면 0.710 x (211,255,255) = (149.8, 181.0, 181.0)
```

두 타입의 실제 차이는 컬링이 아니라 `TransparencyStateShard`(`no_transparency` vs `translucent_transparency`)와 `sortOnUpload`(false vs true)다. 프래그먼트 셰이더의 알파 처리(`if (color.a < 0.1) discard;`)는 두 파일이 동일하다.

### 2026-07-27 — 텍스처 검증 절차: 알파 채널은 파일 포맷에서 봐야 한다

**1차 업로드가 colortype 2(RGB)였다.** 알파 채널 자체가 없고 `tRNS` 청크도 없어, 원래 투명이던 7451픽셀이 전부 흰색 불투명이 되어 있었다. 적용했다면 128×128 흰 상자가 렌더됐다.

**히스토그램만 봐서는 안 된다.** "전 픽셀 알파 255" 는 *리더가 채워 넣은 값*일 수도 있다. IHDR 의 colortype 을 직접 읽어야 구별된다.

**유출 판정은 한 줄로 확정된다.** "이전 파일에서 완전투명이었는데 새 파일에서 비투명인 픽셀" 을 세면 된다. 192개가 전부 `(108..127, 32..51)` 안에 있었다 — 새로 그려진 것은 촉수뿐이고 한 픽셀도 밖으로 나가지 않았다.

**2차 업로드에서 반투명 47픽셀의 RGB 가 바뀌었다.** 알파는 개수·값 모두 동일하고 불투명 8886픽셀의 RGB 도 완전히 동일한데, 반투명 픽셀만 `NEW = OLD/(a/255)` — 프리멀티플라이 해제 값이었다 (41/47 정수까지 일치, 6개는 반올림 차 ±1). 이전 팔레트 PNG 가 프리멀티플라이 상태였고 RGBA 내보내기가 그것을 되돌린 것이다.

### 2026-07-27 — T4: 시선 감쇠와 근거리 반응

**설계서 4.6 범위.** 파라미터 3개를 신설한다.

| key | 기본 | 범위 | 뜻 |
|---|---|---|---|
| `look_damping` | 0.13 | 0 ~ 1 | `current += (target-current) * 이 값` (틱당) |
| `look_damping_near` | 0.06 | 0 ~ 1 | 근거리 계수 |
| `look_near_distance` | 3.0 | 0.5 ~ 16 | 근거리 판정 거리, 블록 |

**`look_damping = 1.0` 은 우회 스위치다.** 필터를 끄고 `current = target` 으로 만들어 T3 상태를 그대로 재현한다. 점화식만으로는 부족하다 — 틱 게이팅과 `partialTick` 보간이 여전히 출력을 한 틱 뒤에 두기 때문에, 계수가 1 이상이면 상태를 곧바로 대입하고 출력도 `target` 자체를 돌려준다.

**범위를 0~1 로 명시한 이유.** 파생 범위(×0.01~×10)를 쓰면 `look_damping` 은 0.0013~1.3, `look_damping_near` 는 0.0006~**0.6** 이 된다. 후자는 우회 스위치 1.0 을 TOML 로 쓸 수 없고, 전자는 발산 구간(>1)까지 열린다.

**근거리 전환은 선형 보간이다.** `0 ~ look_near_distance` 전 구간에 걸쳐 잇는다. 경계에서만 잇는 방식이면 근거리 안쪽에 두 번째 불연속이 생긴다. 계단식이면 3블록 선을 걸어 넘는 순간 목 각속도가 배 이상 뛴다.

#### 바닐라가 이미 하는 평활화 — 실측

설계서를 쓸 때 고려하지 않은 부분이었고, **확인 결과 "지수 평활화가 두 번" 은 아니었다.** 1.20.1 바이트코드:

| 요소 | 값 | 종류 |
|---|---|---|
| `Mob.getHeadRotSpeed()` | **10°/틱** | `yHeadRot` 의 **속도 제한** (`LookControl.rotateTowards`) |
| `Mob.getMaxHeadYRot()` | 75° | 머리-몸통 차 **클램프** |
| `Mob.getMaxHeadXRot()` | 40° | pitch 속도 제한 |
| `LivingEntity.tickHeadTurn` 의 `* 0.3F` | 0.3 | 지수 lerp — **그러나 `Mob` 이 오버라이드해서 실행되지 않는다** |

```
LookControl.rotateTowards(from, to, max) = from + clamp(wrapDegrees(to-from), ±max)
    -> 속도 제한. 꼬리가 없고, 따라잡은 뒤에는 지연이 정확히 0 이다.

Mth.rotlerp(a, b, max) = b - clamp(wrapDegrees(b-a), ±max)
    -> 이름과 달리 lerp 가 아니라 클램프. |b-a| <= max 면 a 를 그대로 돌려준다.

Mob.tickHeadTurn(a, b) { this.bodyRotationControl.clientTick(); return b; }
    -> LivingEntity 의 0.3 지수 lerp 는 이 엔티티에서 죽은 코드다.
```

즉 **우리 감쇠가 유일한 지수 단계다.** 상류는 속도 캡이므로, 머리가 이동 중일 때는 캡이 지배하고 우리 필터가 그 위에 지연을 얹으며, 머리가 도착한 뒤에는 캡이 무력해지고 우리 필터만 남는다.

부수적으로 `BodyRotationControl` 도 확인했다. 머리 변화가 15° 미만인 상태가 10틱 이어지면 이후 10틱에 걸쳐 허용 머리-몸통 차가 75°→0° 로 줄어든다 — **몸이 머리를 따라 돌아 `netHeadYaw` 를 0 으로 몰고 간다.** 정지 상태에서 시선 target 이 저절로 0 으로 수렴하는 것은 이 때문이다.

#### T4 실측

### 2026-07-27 — GeckoLib 4.8.4 의 `catmullrom` 이 깨져 있다 (사양 충돌)

**4.4.2 의 "전 구간 `lerp_mode: catmullrom`" 을 이 버전에서는 지킬 수 없다.**

`EasingType$CatmullRomEasing.apply` 는 `easingArgs` 가 2개 미만이면 이렇게 한다:

```
lerp(easedT, start, end)          <- CatmullRomEasing
lerp(start, end, easedT)          <- 그 외 모든 이징의 기본 apply
```

`Interpolations.lerp(a, b, x) = a + (b - a) * x` 이므로 인자 순서가 뒤바뀐 것이다. 게다가 헬퍼 `catmullRom(n)` 은 전개하면 **`n + 2`** 로, 시간 항이 전부 상쇄된 상수 오프셋이다.

**실측** (start −18 → end +18, 구간 10틱):

```
n=0.00 -> -341.0    n=0.40 -> -347.8    n=0.80 -> -320.6
n=0.10 -> -342.7    n=0.50 -> -315.5    n=0.90 -> -322.3
n=0.20 -> -344.4    n=0.60 -> -317.2    n=1.00 ->  +18.0
n=0.30 -> -346.1    n=0.70 -> -318.9
```

같은 조건에서 `linear` 는 −18 → +18 을 정상적으로 지난다.

**`easingArgs` 를 주는 우회로도 막혀 있다.** 2개를 주면 올바른 `getPointOnSpline(t, p0, p1, p2, p3)` 분기로 가지만, `BakedAnimationsAdapter` 는 하나의 `easingArgs` 리스트를 **x/y/z 세 축의 `Keyframe` 에 그대로 공유**시킨다. 축마다 다른 제어점을 줄 수 없고, 상수 0 인 축까지 그 제어점으로 휘어 버린다.

**임시로 `linear` 를 쓴다. 사양 변경이 아니라 대기 상태다.** 선택지는 (a) linear 유지 (b) GeckoLib 판올림/패치 (c) 스플라인을 Java 에서 직접 계산. 판단 대기.

### 2026-07-27 — json 키프레임 경로의 축별 부호 실측 (T5)

**T1 축 검증은 Java `setRot*` 경로만 확인했다.** 걷기는 json 키프레임이고, 두 경로가 같은 부호를 쓴다는 보장은 없었다. 그리고 대칭값(leg ±18, arm ±10, body.yRot ±3)으로는 min/max 가 같아 판별이 불가능하다 — `body.xRot` 만 비대칭 상수였기에 드러났다.

**절차.** 임시 애니메이션 `signtest` 에 본마다·축마다 **서로 다른 양수 상수**를 넣었다. 전부 양수이므로 음수가 도달하면 부호 반전이고, 크기가 전부 다르므로 축이 뒤바뀐 경우도 값으로 특정된다. 기여 = (signtest 창의 값) − (기준선 창의 값).

| 본 | json x/y/z | 본에 도달한 기여 x/y/z | 배율 |
|---|---|---|---|
| body | +11 / +12 / +13 | −11.000 / −12.000 / +12.943 | −1 / −1 / +1 |
| hip | +21 / +22 / +23 | −21.000 / −22.000 / +23.000 | −1 / −1 / +1 |
| head | +31 / +32 / +33 | −31.000 / **−32.000** / +33.000 | −1 / −1 / +1 |
| arm_right | +41 / +42 / +43 | −41.000 / −42.000 / +42.650 | −1 / −1 / +1 |
| arm_left | +51 / +52 / +53 | −51.000 / −52.000 / +53.350 | −1 / −1 / +1 |
| leg_right | +61 / +62 / +63 | −61.000 / −62.000 / +63.000 | −1 / −1 / +1 |
| leg_left | +71 / +72 / +73 | −71.000 / −72.000 / +73.000 | −1 / −1 / +1 |

**결론 — 예외 없이 균일하다.**

```
json 키프레임 -> 본 :   xRot  x(-1)      yRot  x(-1)      zRot  x(+1)
Java setRot*  -> 본 :   xRot  x(+1)      yRot  x(+1)      zRot  x(+1)   (T1 검증)
```

21개 측정 중 x·y 14개가 전부 정확히 −1.000, z 7개가 전부 +1.000 이다. 축 뒤바뀜은 없다 — 크기가 전부 대응하는 값과 일치한다.

**`head.yRot` 은 1차 측정에서 판별 불가였다.** 시선 Goal 이 ±75° 를 무작위로 쓸어 min/max 중앙값이 기준선 노릇을 못 했다(기여 −2.469 로 나옴). `look_gain 0` 으로 시선 기여를 끄고 재측정해 −32.000 을 얻었다. **값만 보고 판정할 수 없는 항목이 있으면 명시하라는 절차가 실제로 한 건을 걸러냈다.** (`look_gain` 은 런타임 파라미터이고 일회용 검증 월드에서만 바꿨다. 리포지토리에는 변경이 없다.)

**이것이 `body.xRot` 불일치의 원인이다.** json 의 `-4` 가 본에 `+4` 로 도달한다. 그리고 **걷기 전체가 x축에서 앞뒤가 뒤집혀 있다** — 다리·팔의 스윙 방향과 0틱의 대각선 협응(오른다리 뒤 + 오른팔 앞)이 전부 반대다. `body.yRot`(좌우 체중)과 `head.yRot`(반대회전)도 뒤집혀 있으나, 이 둘은 서로 부호가 반대인 쌍이라 **상대 관계 `head.yRot = body.yRot × −0.4` 자체는 유지된다.**

**임시 변환으로 덮지 않았다.** 두 경로의 부호가 다른 것 자체가 사양 결함이며, 어느 쪽을 기준으로 삼을지와 변환을 어디에 둘지는 사람이 정한다. `signtest` 애니메이션과 `/wardengirl signtest <on|off>` 는 판정이 끝나면 삭제한다.

### 2026-07-27 — 부호 기준을 Java 규약으로 확정. 변환 1차 시도는 검증 실패

**Part 4.0 추가 조항:**

> **json 키프레임의 x/y 부호는 본 회전과 반대다.** 설계서 값은 본 기준으로 쓰고, 적용 시점에서 반전한다. json 파일을 직접 읽을 때 부호가 반대로 보이는 것은 정상이다. z 축은 일치하므로 건드리지 않는다.

**변환 지점 — `AxisConvention` 이 아니다.** `AxisConvention` 은 도↔라디안의 단일 지점이지만 **Java 경로** 위에 있다. 정적 오프셋·시선 가산·headgear 스프링이 전부 그것을 거치고, 셋 다 이미 올바른 부호로 작동한다. 거기에 반전을 넣으면 그 셋이 뒤집힌다. 두 경로에 서로 다른 변환이 필요하므로 클래스를 나눴다 — `JsonAxisConvention` 은 `WardenGirlModel.getAnimation` 한 곳에서만 호출되고, 그 지점은 json 경로 전용이다.

**Java 경로 3종은 변환 전후 동일하다 (실측).**

```
정적 오프셋 arm_right x   전 +4.000~+4.000   후 +4.000~+4.000   동일
정적 오프셋 arm_left  x   전 +4.000~+4.000   후 +4.000~+4.000   동일
정적 오프셋 leg_right y   전 +2.000~+2.000   후 +2.000~+2.000   동일
정적 오프셋 leg_left  y   전 -2.000~-2.000   후 -2.000~-2.000   동일
정적 오프셋 head      x   전 -3.250~-2.750   후 -3.250~-2.750   동일
정적 오프셋 body      x   전 -2.000~-1.000   후 -2.000~-1.000   동일
스프링 headgear_right z   전 -5.189~-4.793   후 -5.206~-4.796   동일
스프링 headgear_left  z   전 +4.798~+5.221   후 +4.780~+5.218   동일
```

`시선 head y` 와 `스프링 headgear_left y` 는 시선 Goal 이 ±75° 를 무작위로 쓸어 창마다 대역이 달라진다. **판별 불가 항목이며, 위 8개가 소수점 셋째 자리까지 동일하다는 것이 의미 있는 부분이다.**

#### 검증 실패 — 배율 +1.000 이 아니라 값이 라디안으로 나온다

`signtest` 21항목 중 z 7개는 `+1.000` 으로 정상이지만, **x/y 14개가 전부 어긋난다.**

```
json +61 (leg_right x)  ->  본 -1.065        기대 +61
json +62 (leg_right y)  ->  본 -1.082        기대 +62
json +11 (body      x)  ->  본 -0.19 부근     기대 +11
```

**값이 정확히 `-(json도 × π/180)` 이다.**

```
-(61 x pi/180) = -1.0647   실측 -1.065
-(62 x pi/180) = -1.0821   실측 -1.082
-(11 x pi/180) = -0.1920   실측 -0.19 부근
```

즉 부호는 반전됐으나 **도→라디안 변환이 한 번 더 걸렸다.** `Keyframe` 을 재구성하면서 GeckoLib 이 베이크 때 씌워 둔 무언가를 잃은 것으로 보인다. 원인 미특정이며 **추측으로 π/180 을 곱해 덮지 않았다** — 그렇게 하면 값은 맞지만 이유를 모르는 채로 남고, 같은 자리에서 다시 깨진다.

`z` 축이 정상인 것이 단서다. `z` 는 `negate()` 를 거치지 않고 원본 리스트를 그대로 넘긴다. 따라서 문제는 반전 로직이 아니라 **`new Keyframe<>(...)` 재구성 자체**에 있다.
