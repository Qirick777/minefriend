### 1-A 에서 확정된 값

- `LookControl.getWantedX/Y/Z()` descriptor = `()D` (**double**). `EntityDataSerializers` 에 `DOUBLE` 이 **없다** → `FLOAT` 사용, double→float 축소 발생. **실측 최대 축소 오차 `0.000001817` 블록**.
- `isLookingAtTarget()` = `()Z` → `BOOLEAN`.
- 검증 키는 **동기화 순번**이다. 좌표 폴링으로 만든 두 열에는 짝지을 키가 없어 이전 라운드에 183/183 대응 실패가 났다. 순번을 **마지막에** 올리므로 클라가 새 seq 를 본 시점에는 네 값이 이미 그 seq 의 것이다.
- `ServerEntity.sendChanges()` 는 `entityData.isDirty()` 일 때만 보낸다. 같은 틱의 여러 `set` 은 dirty 병합되어 한 패킷이 되므로 **중간 seq 건너뜀은 오류가 아니다.**
- `broadcastAndSend` 는 `Consumer<Packet<?>>` 에 **패킷 인스턴스를 한 번** 넘긴다. 수신자별 payload 재계산 분기 없음.

## 3. 1-B-1 확정 구현 사항

### 3.1 실제 LookAt 대상 접근

```java
public class WardenGirlLookAtPlayerGoal extends LookAtPlayerGoal {
    // 생성자 인수를 그대로 상위 생성자에 전달
    public Entity getLookAt() {
        return this.lookAt;
    }
}
```

- `LookAtPlayerGoal.lookAt` 은 **`protected net.minecraft.world.entity.Entity`** — 바이트코드 확인. 하위 클래스에서 직접 읽을 수 있다.
- **리플렉션 금지. 캐스팅 금지. 제품 getter 의 `instanceof` 필터 금지.**
- Goal 정책 메서드는 **재정의하지 않는다.**
- 정상 런타임 값은 `Player` 또는 `null` 이다 (`Player.class` 로 등록했고 `canUse()` 의 Player 분기가 `getNearestPlayer(...)` 로 채운다). 타입 검사는 **검증 불변조건으로만** 둔다.

### 3.2 Goal 상태 판정

엔티티가 두 인스턴스를 **필드로 보유**하고, `goalSelector.getRunningGoals()` 의 실제 Goal 객체와 `==` 로 비교한다.

- 워든걸 전용 `LookAtPlayerGoal`
- `RandomLookAroundGoal`

**클래스 이름 문자열을 제품 판정에 사용하지 않는다.**

현재 등록 (`WardenGirlEntity.registerGoals`): `FloatGoal` 0, `LookAtPlayerGoal(this, Player.class, 12.0F)` **7**, `RandomLookAroundGoal(this)` **8**. 둘 다 `Goal.Flag.LOOK` 이라 배타이고 7이 이긴다. **직전 실측에서 두 LOOK Goal 동시 실행 0건.**

### 3.3 감쇠 거리

- `LookAtPlayerGoal` 활성 + 대상 존재 → `wardenGirl.distanceTo(lookAtGoal.getLookAt())`
- `RandomLookAroundGoal` 활성 → far 감쇠값
- `wanted == false` → far 감쇠값

**목표 좌표까지의 거리 금지. 별도 최근접 플레이어 검색 금지. 클라이언트 로컬 플레이어 사용 금지.**

`LookAtPlayerGoal` 활성인데 대상이 `null` 이면 임의 대체하지 말고 **오류 계측 후 해당 틱을 불통과 표본으로 기록**한다.

## 4. 확정 바닐라 규칙 (1.20.1 바이트코드 실측)

| 항목 | 값 | 출처 |
|---|---|---|
| yaw 속도 상한 | **10 °/tick** | `Mob.getHeadRotSpeed()` |
| pitch 속도 상한 | **40 °/tick** | `Mob.getMaxHeadXRot()` |
| 몸통 대비 yaw 제한 | **±75°** | `Mob.getMaxHeadYRot()` |
| 목표 world yaw | `degrees(atan2(dz, dx)) - 90` | `LookControl.getYRotD()` |
| 목표 entity pitch | `-degrees(atan2(dy, horizontalDistance))`, `dy = wantedY - eyeY` | `LookControl.getXRotD()` |
| idle yaw | 몸통 방향으로 `10 °/tick` 복귀 — `rotateTowards(yHeadRot, yBodyRot, 10.0F)` | `LookControl.tick()` else 분기 |
| idle pitch | 매 틱 0 — `resetXRotOnTick()` = true | `LookControl.tick()` |
| 회전 제한 | `from + clamp(wrapDegrees(to - from), -max, +max)` | `LookControl.rotateTowards` |
| 본 규약 변환 | `yaw = -wrapDegrees(headYaw - yBodyRot)`, `pitch = -entityPitch` | GeckoLib `EntityModelData` 가 `-netHeadYaw` / `-headPitch` 로 준다 |

**실제 엔티티 `yHeadRot` 을 shadow 누적 상태로 사용하지 않는다** — 탑승 중 `Boat.clampRotation` 이 매 틱 `yHeadRot = yRot` 로 덮는다.

### 참고 — 왜 서버 각도를 그대로 못 쓰는가 (이미 확정된 조사 결과)

- `Boat.clampRotation(passenger)`: `setYBodyRot(boat.getYRot())` → yRot 을 보트 ±105° 로 clamp → **`setYHeadRot(passenger.getYRot())`**.
- `Entity.rideTick()` = `tick()` → `positionRider`. 그래서 `tick()` 안에서 Goal 이 만든 `yHeadRot` 은 **같은 틱 끝에 지워진다.**
- 실측: `aiStep()` 직후와 `tick()` 끝의 `yHeadRot` 이 560틱 전부 동일(차이 0.000). 캡처 지점을 옮겨도 소용없다. **각도는 죽지만 Goal 판정(running / wanted / wantedX/Y/Z)은 살아 있다.**

## 5. 프로젝트 규칙

| 파라미터 | 값 |
|---|---|
| `LOOK_GAIN` | 1.0 |
| `LOOK_YAW_MAX` | 75 |
| `LOOK_PITCH_MAX` | 35 |
| `LOOK_DAMPING` | 0.5 |

**처리 순서 (clamp 후 감쇠를 유지한다)**

1. 바닐라 목표각
2. 바닐라 속도 제한
3. 몸통 대비 yaw 제한
4. 본 규약 변환
5. gain
6. 프로젝트 yaw/pitch clamp
7. 지수 감쇠

> clamp 를 먼저 하는 이유는 기존 `applyLook` 주석에 있다 — 감쇠 후 clamp 하면 목표가 범위 밖인 동안 머리가 한계에 붙박이고 접근 궤적이 직선으로 잘린다.

## 6. 서버 shadow 상태기계

**서버 틱당 정확히 한 번** 갱신되는 엔티티별 상태기계.

필요 상태: 초기화 여부 / 직전 탑승 여부 / world head yaw / entity pitch / 감쇠 이전 yaw·pitch / 감쇠 최종 yaw·pitch.

- `wanted == false` 이면 **stale X/Y/Z 를 계산 입력으로 사용하지 않는다** (로그 표시는 가능).
- 탑승 시작 시 **몸통 정면과 pitch 0** 으로 초기화.
- 하차 시 shadow 상태 초기화 또는 폐기.
- **지상 시선에는 적용하지 않는다.**

읽는 지점은 **`aiStep()` 직후**다. 관문 측정을 통과한 위치이고, `hasWanted` 는 매 틱 리셋되며 `clampRotation` 은 그 뒤에 온다. 이미 `WardenGirlEntity.aiStep()` 오버라이드가 그 지점에 있다.

## 7. 서버 안전 감쇠 계산기

클라이언트 패키지의 `com.wardengirl.client.LookDamper` 를 **서버에서 참조하지 않는다.** 서버 또는 공용 패키지에 순수 계산기를 새로 만든다.

금지: `Minecraft` 참조 / 렌더 클래스 참조 / `partialTick` / 프레임 단위 상태 갱신 / 클라이언트 로컬 입력.

recurrence 는 기존과 동일하다.

```
current += (target - current) × damping
```

계수 clamp 도 기존 `LookDamper` 와 같게 재현한다. 1-B-1 에서는 렌더 보간 출력을 만들 필요가 없다 — **서버 틱 최종값**만 산출·기록한다.

### 불변조건 — 위반 횟수를 전부 보고

| 조건 | 검사식 | 허용 오차 |

| 프로젝트 pitch clamp 초과 | `abs(pitch_clamp후) ≤ 35` | 1e-4 |
| 감쇠 recurrence 잔차 | `abs(out - (prev + (tgt - prev) × k))` | 1e-6 |
| `wanted=false` stale 좌표 소비 | stale 좌표를 바꿔도 idle 출력 불변 | — |
| NaN / Infinity | 0건 | — |
| Goal 활성 + 대상 null | 0건 | — |
| Goal 활성 + 대상 비-Player | 0건 | — |
| 두 LOOK Goal 동시 실행 | 값과 호출 순서만 보고, 우선순위를 만들지 말 것 | — |

## 14. 작업 규칙 (누적된 것)

- **Part 6.5 형식으로 보고하고 정지한다.** `[사람 확인]` 항목은 절대 스스로 판정하지 않는다.
- **검증은 값으로 한다.** "성공" 문자열은 검증이 아니다. 실제 관측값을 출력한다.
- **측정 유효 조건을 먼저 적는다.** 조건이 0이면 통과가 아니라 **측정 불가**다.
- **확실하지 않은 것을 임의로 정하지 않는다. 묻는다.**
- **API 사실은 바이트코드로 확인한다. 추측하지 않는다.**
- **사양 오류를 발견하면 보고하되 임의로 바꾸지 않는다.**
- **지시문의 평가에 사실 오류가 있으면 즉시 짚고, 그 평가에 근거한 지시는 실행하지 않는다.**
- **하나라도 악화되면 보고하고 멈춘다.** 진행 상황을 왜곡하지 않는다.
- **컨텍스트가 부족하면 나눠서 보고한다. 반쪽 상태로 보고하지 않는다.**
- 캡처는 명시적으로 요청받았을 때만 찍는다.
- Java 파라미터 구동 자세는 `ClipAudit` 대상이 아니다 (클립 데이터가 없다).
- Java 가 `+=` 로 쓰는 채널은 매 프레임 어떤 클립이든 대입해야 한다. `ClipStructureCheck.JAVA_ADDED` 로 강제한다.
